---
title: "Assign"
description: "Give learners a published role play to practise."
---

An assignment lets a learner practise a published role play through a personal link (`practiceUrl`), as many times as their credits allow. A learner can only practise the role plays assigned to them. For the whole flow, from assigning to reading the result, see [Role plays end to end](/guides/role-plays).

## Before you assign

You need:

- A learner `userId` from `GET /users`, or just an `email`—never both in the same request. Someone new is added to your organization as a learner first (with their starting credits), in the same request.
- A published scenario slug from `GET /scenarios` or the TrainerTwin dashboard.

Scenario and persona configuration remains dashboard-only.

## Create an assignment

```bash
curl "https://dash.trainertwin.com/api/v1/assignments" \
  --request POST \
  --header "x-api-key: $TRAINERTWIN_API_KEY" \
  --header "content-type: application/json" \
  --data '{
    "userId": "user_123",
    "scenario": "react-mock-interview"
  }'
```

A new assignment returns `201`:

```json
{
  "assignment": {
    "id": "assignment_123",
    "assignedAt": "2026-09-01T09:30:00.000Z",
    "userId": "user_123",
    "email": "avery@example.com",
    "scenario": "react-mock-interview"
  },
  "practiceUrl": "https://your-org.trainertwin.com/s/AbC123",
  "created": true,
  "emailSent": true
}
```

`practiceUrl` is the learner's personal practice link. Send it through your own channel instead of, or alongside, the TrainerTwin email. It works only for the learner it was assigned to: they sign in with that email (Google or a code sent to it).

The email, **New role play: *name***, names the role play and its objective, says how many credits (minutes of practice) the learner has, and which email to sign in with. Someone new to your organization is told they were added, in the same email.

Creating the same learner-scenario pair again is safe. While the assignment is pending or used, TrainerTwin returns it with `created: false` and does not send another email. A cancelled or expired assignment is reopened instead: it gets a new `practiceUrl`, the learner gets an email, and the response is `201` with `created: true`.

`userId` is always the learner's: assigning by email adds them to your organization first.

<Note>
  Assignment persistence succeeds even when email delivery fails. Check `emailSent` instead of retrying the assignment immediately.
</Note>

## Credits

Someone new to your organization's credits gets **30** (1 credit = 1 minute of practice) from its prepaid balance when first assigned. If the balance can't cover them, the request returns `409` and nothing is assigned. Credits belong to the learner and are shared by every role play and twin, so assigning more role plays doesn't give more credits. A call ends when the learner's credits run out. Give learners more through `POST /users/{id}/credits` with an Idempotency-Key, or in the dashboard. See [Credits](/guides/credits).

## Practising again

There's no limit on attempts while credits and access remain. Each new practice uses the same `practiceUrl`; a still-live call may be rejoined. The assignment remains `pending` even after practice (historical `used` links still work). Use `practiceCount`, not status, to count practices. List its sessions with `GET /sessions?assignmentId=…`.

## Change an assignment

Move an assignment to another learner, scenario, or both:

```bash
curl "https://dash.trainertwin.com/api/v1/assignments/assignment_123" \
  --request PATCH \
  --header "x-api-key: $TRAINERTWIN_API_KEY" \
  --header "content-type: application/json" \
  --data '{ "scenario": "system-design-interview" }'
```

You can also move it to an `email` address. A changed assignment sends a notification to the target learner and returns a new `practiceUrl` (the old link stops working). Moving it to someone new to your organization's credits gives them their 30 first, or returns `409` when the balance can't cover them. A no-op or repeated completed move returns `changed: false`, the existing target `practiceUrl`, and sends no email. Recipient checks still apply. Moving onto an already-open learner/scenario pair returns `409`; a closed target pair is reopened with its historical assignment ID. Concurrent requests cannot create two destinations from the same source.

## Inspect an assignment

```bash
curl "https://dash.trainertwin.com/api/v1/assignments/assignment_123" \
  --header "x-api-key: $TRAINERTWIN_API_KEY"
```

Returns the learner, scenario, current `status`, `practiceUrl`, how often it was practised (`practiceCount`), and when last (`lastPracticedAt`, or `null`). `status` is `pending` (open, whether practised or not), historical `used` (also open), or `cancelled`. Assignments made before links stopped expiring may show `expired`; assigning again reopens them.

List assignments with `GET /assignments`, filtered by `userId` or `email` (never both), and optionally `scenario`.

## Remove an assignment

```bash
curl "https://dash.trainertwin.com/api/v1/assignments/assignment_123" \
  --request DELETE \
  --header "x-api-key: $TRAINERTWIN_API_KEY"
```

DELETE succeeds only for a pending assignment with **no associated sessions**. Used, cancelled, expired or session-linked assignments return `404`, as does a repeated delete. No scenario/history is deleted and no credits are refunded. Use learner disable to remove all of a learner's access; moving an assignment cancels its old link.
