# People and emails

> Despite this file's old name, org invitations are gone. Adding a person makes them a member immediately. Twin/role-play assignment first adds the learner, then gives account-bound access. Each action builds one combined email per affected person, normally delivered by `send-emails`. Sign-in codes and support alerts use the shared Resend sender; billing uses its own billing@ sender through the same transport. Owners: `web/lib/org-people.ts`, `web/lib/invite/*`, `web/lib/email.ts`, `web/lib/queue-emails.ts`. Agreed rules: [People](people.md).

## Who uses it

| Actor | Action / pointer |
| --- | --- |
| Admin/team | Add team or learners in Settings, assign practice, grant learner credits (`web/lib/minutes-trpc.ts`; `web/lib/twin/trpc.ts`; PUT `web/app/api/role-play/[slug]/assignments/route.ts`). |
| Learner | Signs in with an existing account and uses their access (`web/lib/pages/learner.ts`; see [Auth](auth.md)). |
| API integrator | Adds learners and assigns role plays (`web/app/api/v1/users/route.ts`; `web/app/api/v1/assignments/route.ts`). |
| Copilot | Assigns learners, refusing staff recipients (`web/lib/copilot-studio.ts` `inviteLearners`). |
| Operator | Creates founder account/token, prints onboarding URL; no founder email (`web/scripts/founder-invite.ts`). |
| Reporter/support | Saves issue / receives alert (`web/app/api/issues/route.ts`; `web/lib/issue-alerts.ts`). |

## Data

- Org people are `User`/`Member`; [Organizations and roles](orgs-and-roles.md) owns their lifecycle. Assignments require owners and have no recipientEmail. Twin unique `(agentId,userId)`; role play unique `(deploymentId,memberId)` (`web/prisma/schema.prisma`; `20261111120000_people_first/migration.sql`).
- `Invitation` stays as historical data. Migration closes all pending rows as accepted. New Better Auth invite-member requests fail; old `/invite` pages only redirect. There is no awaiting-user pool (`web/lib/auth.ts` `beforeCreateInvitation`; `web/app/auth/invite/page.tsx`).
- `OutboundEmail` is person or orgCredits plus optional idempotencyKey, carried by a workflow, not an app email table. Progress: sent/failed per address, then done with sent count/failed addresses (`web/workflows/send-emails.ts`).
- `OrgBilling.announcedGrantIds` stores announced Meteroid grant IDs. Migration initializes it from existing grants, avoiding historical announcements (`web/lib/org-credits-email.ts`; people-first migration).
- Billing email completion lives on `BillingInvoice`: issuedEmailAt, reminderAt, overdueEmailAt (paused or upgrade-cancelled), paidEmailAt. Workflow claims are issuedRunAt/paidRunAt. `invoicePdfKey` / `receiptPdfKey` reference each first-drawn S3 PDF; those bytes are kept separately from email completion. Billing does not use the person-email `OutboundEmail` payload (`web/prisma/schema.prisma` `BillingInvoice`; `web/lib/billing/billing.ts` `EMAIL_FIELD`, `claim`, `emailOnce`, `keptPdf`; [Billing code](billing-code.md)).

## How it works

### Add people, then notify

Settings `minutes.addPeople` accepts team/user and 1–50 normalized valid emails. New learners get optional whole starting minutes 1–360 (default 30). The `add-org-people` workflow calls `addOrgPeople`, then queues emails. Existing members keep roles and count as already; disabled/studio learner recipients are refused for the batch. There is no acceptance step for any role (`web/lib/minutes-trpc.ts`; `web/lib/workflow-runs.ts` `runAddOrgPeople`; `web/workflows/add-org-people.ts`; `web/lib/invite/org.ts`; [Organizations and roles](orgs-and-roles.md)).

`addedEmails` sends only new memberships, key `added:<memberId>`, with actor, org, role and learner balance/starting credits. Learner sign-in link is org home; admin/team is studio (`web/lib/invite/org.ts`; `web/lib/invite/person-email.ts` `personEmailFor`; `web/lib/invite/links.ts` `signInUrl`).

REST POST users calls `addLearnerByApi`, not an invitation writer. requireExternalApi first checks the enabled admin/team key creator; no creator fallback remains. The helper calls addPeopleToOrg and sends only a new member's combined email inline, with background retries on failure. It returns 201 new / 200 existing `{user,created,emailSent}`; no email for existing learner. AppErrors preserve `{error,code}` and their status: person_disabled/person_is_studio or short credits 409, api_key_owner_gone 403, paused credits 403, invalid input from the service 400. Route schema errors still omit code (Mismatches). GET lists enabled learners and always invitations=[] (`web/lib/external-api.ts` `requireExternalApi`; `web/app/api/v1/users/route.ts:41–57`; `web/lib/invite/org.ts` `addLearnerByApi`; see [Public API](public-api.md)).

### Assign twins or role plays

Both assignment writers run inside addPeopleToOrg's then callback in the same minutes/people-locked transaction as checks, starting credits, accounts and members (Practice 10/19); a batch persistence failure rolls all of those back. Existing members receive no starting grant. Email building follows after commit; a brand-new learner gets one combined email containing added, practice and actual starting credits (`web/lib/org-people.ts:126–173`; `web/lib/invite/twin.ts:24–56`; `web/lib/invite/roleplay.ts:32–60`; see [Twins](twins.md) and [Role plays](roleplays.md)).

| Kind / prior state | Write / email |
| --- | --- |
| Twin absent | Create active by userId, fresh code; email readable `/t/` URL, optional until and current balance. |
| Twin revoked | Reactivate, rotate code, replace end date; email. |
| Twin active (even past end date) | Skip; no date update/email. |
| Role play absent / cancelled / expired | Create or reopen pending by memberId, fresh code/date, clear usedAt; email personal `/s/` URL. |
| Role play pending, resend requested | Same code/date, new time-based email event key. |
| Role play pending without resend / used | Skip, no email. |

Pointers: `web/lib/twin-access.ts` `assignTwin`; `web/lib/invite/twin.ts`; `web/lib/invite/roleplay.ts`. Role-play expiry is stored 30 days ahead but not enforced for pending/used access; twin optional accessUntil gates new starts ([Twins](twins.md), [Role plays](roleplays.md)).

`assign-twin` / `assign-roleplay` workflows queue returned emails once. Counts include joined (new members) and assignment added/reactivated/resent/skipped. REST role-play POST/PATCH uses assignScenario: email/member and assignment writes are locked together; userId lookup refuses disabled/studio recipients (Practice 19; `web/lib/external-api-assignments.ts:31–60`). Live POST or same-pair PATCH returns unchanged without email; a move rotates link. REST email key is `assignment:<id>:<shareCode>` (`web/lib/workflow-runs.ts`; `web/workflows/assign-{twin,roleplay}.ts`; `web/lib/external-api-assignments.ts`; assignment routes).

Readable Share creates a URL, not enrollment. Opening an active common `/s/` link uses join=true to add the signed-in existing account through addPeopleToOrg, grant starting credits once and create/reuse an assignment, without email. Activation uses join=false and never adds anyone; a nonmember direct start is refused. Disabled common link or revoked/ended existing assignment refuses access (`web/lib/twin/trpc.ts` `agents.shareLink`; `web/lib/twin-access.ts` `twinAccessByCode`; `web/lib/pages/learner.ts` `loadSharedSession`; `web/lib/interview-sessions.ts` `activateSession`).

Copilot filters staff through `studioPeopleEmails`, then invokes the shared helpers for others. It ignores legacy minutes and sends no studio membership invitation. Deleted `assign-session-invite.ts` / `create-session-invite.ts` are no longer entry points (`web/lib/copilot-studio.ts`; commit `1d1ed9f`).

### Grant credits and notify

`give-credits` runs `giveLearnerCredits`: resolve orgPeople including disabled, skip nonmembers/staff/disabled/cap overflow, grant the remaining learners all-or-nothing for org funds, then one credits email per given person. Key `credits:<orgId>:<email>:<request timestamp>`; includes amount and new whole balance (`web/lib/invite/credits.ts`; `web/lib/minutes-trpc.ts` `add`, `addMany`; `web/workflows/give-credits.ts`; [Credits](credits.md)).

`sync-org-credits` refreshes, then its announce step calls `announceNewGrants`. Each positive cached grant not in announcedGrantIds sends the enabled admin an orgCredits email, key `org-credits:<grantId>`, amount, cached balance, expiry/reason and studio credits link. Successful batch pushes IDs. Missing admin or missing Resend also marks IDs announced; other send failures throw and retry the whole announce step (`web/workflows/sync-org-credits.ts`; `web/workflows/steps/org-credits.ts` `announce`; `web/lib/org-credits-email.ts`).

### Billing emails

[Billing rules](billing.md) and [Billing code](billing-code.md) own invoice events and payment effects. Staff create each org's own CUSTOM subscription in Meteroid; its first live non-`Credits` subscription invoice is adopted as an upgrade. The app has no upgrade request/procedure/button; Trial's Billing page says to contact TrainerTwin. Choosing/switching plans is future work, issue #19 (`web/lib/billing/billing.ts` `kindOf`; `web/lib/billing/trpc.ts` `billingRouter`; `web/components/billing/billing-page.tsx` `PlanSection`; [Billing](billing.md) rules 2, 10). The invoice workflows call `emailOnce`, then `web/lib/email.ts` `sendBillingEmail` / `billingEmail`, not the person-email queue. Default sender: `TrainerTwin Billing <billing@trainertwin.com>` (BILLING_FROM_EMAIL override), reply-to support@trainertwin.com. Recipients: current billing-detail emails, otherwise the enabled org admin; no recipient logs and sends nothing (`web/lib/billing/billing.ts` `recipients`, `emailOnce`).

| Event | Current subject / content | Attachments / marker |
| --- | --- | --- |
| Invoice issued, any kind | `Your TrainerTwin invoice <number>: <amount> due <date>`; org, description, tax-inclusive amount, due date and Pay now, or reply for a payment link. | App invoice `<number>.pdf` / issuedEmailAt |
| Unpaid renewal due tomorrow | `Reminder: invoice <number> (<amount>) is due tomorrow`; due date, Pay now or reply for a payment link, pause warning, reply if already paid. Only on the UTC day before due. | App invoice `<number>.pdf` / reminderAt |
| Overdue current renewal, org paused | `Your TrainerTwin plan is paused: invoice <number> is overdue`; no new calls/grants, Pay now or reply for a payment link, reply if paid. | App invoice `<number>.pdf` / overdueEmailAt |
| Unpaid upgrade cancelled | `Your upgrade to the TrainerTwin Paid plan was cancelled`; remains Trial; says to reply to the email to upgrade again (staff do upgrades). | None / overdueEmailAt |
| Invoice paid, any kind | `Payment received for invoice <number>: thank you`; amount/description, plan activation (or staff follow-up for an unmatched/cancelled lost-ID upgrade), current active/still-paused renewal outcome, or pack credits being added separately. | App receipt `RCPT-<number>.pdf` then app invoice `<number>.pdf` / paidEmailAt |

**Phase 3 Pay now:** `emailOnce` supplies the saved payment URL only for a locally unpaid invoice. Issued, reminder and paused HTML show a “Pay <amount> now” button opening Razorpay in a new tab; plain text says “Pay online: <URL>”. Without a URL, both say “To pay invoice <number>, reply to this email and we'll send you a payment link.” No bank details/instructions remain. Paid and upgrade-cancelled templates have neither payment button nor reply-for-link fallback. A newly drawn unpaid invoice PDF prints a clickable “Pay online” URL when supplied; without a URL it says “To pay, write to <seller email> for a payment link, quoting <number>.” If the seller email is empty it says “us”. With S3 configured, paid mail attaches the first kept invoice copy: it can retain the link or no-link guidance from when unpaid. Only a PDF first drawn after payment omits that guidance (`web/lib/billing/billing.ts` `invoicePdf`, `keptPdf`, `emailOnce`; `web/lib/email.ts` `billingEmail`; `web/lib/billing/documents.ts` `renderInvoice`). Razorpay is always on: the invoice-issued workflow tries its `payLink` step before emailing. Missing `RAZORPAY_KEY_ID` or `RAZORPAY_KEY_SECRET` throws on link creation, but the workflow catches that failure and sends invoice mail without Pay now, asking for a reply. Daily repair retries the missing link; a late link does not resend an already completed email or add a URL to an already kept PDF (B20; `web/lib/razorpay.ts` `env`, `call`; `web/lib/billing/razorpay.ts` `ensurePaymentLink`; `web/workflows/invoice-issued.ts` `invoiceIssued`; `web/lib/billing/billing.ts` `syncOrgInvoices`; [Billing code — Mismatches](billing-code.md#mismatches)).

Pointers: `web/lib/email.ts` `billingEmail`; `web/lib/billing/billing.ts` `invoiceIssuedEmail`, `invoiceReminder`, `invoiceOverdue`, `invoicePaid`, `emailOnce`. HTML is escaped; plain text uses the same values, with amounts formatted in the invoice currency (`web/lib/billing/pricing.ts` `formatMoney`) and a See billing link to `dash.<base>/billing`. `BILLING_PAYMENT_INSTRUCTIONS` and `BillingEmailArgs.paymentInstructions` have been removed; old environment values have no effect on app mail/PDFs. Customers pay through Razorpay only (card or bank transfer where Razorpay offers it); optional bank transfers, such as International bank transfers / MoneySaver, are enabled in Razorpay itself. Staff can still record payments made outside Razorpay in Meteroid ([Billing](billing.md) rule 20; `web/lib/email.ts` `BillingEmailArgs`, `billingEmail`; `web/lib/billing/billing.ts` `emailOnce`, `invoicePdf`, `invoicePaid`; `web/lib/billing/documents.ts` `renderInvoice`; `web/components/billing/billing-page.tsx` `InvoicesSection`).

Each invoice/event has a durable marker plus Resend key `billing-<event>-<invoice id>` (`event`: issued, reminder, paused, upgrade_cancelled, paid). Markers prevent ordinary retries after the provider's 24-hour key window; the key covers overlapping sends inside that window. Both PDFs are first drawn by the app in one Stripe-like layout from Meteroid's invoice JSON, using its issued `customer_details` snapshot, not current buyer billing details; only a missing customer name falls back to the current org name. Seller name/address/GSTIN/contact email and LUT ARN come from Meteroid's **default invoicing entity** when first drawing, edited in Meteroid Settings › Invoicing entity. `sellerDetails()` reads it over gRPC-web, caches successful results for 10 minutes and throws without an entity, legal name or GSTIN. `defaultInvoicingEntity` decodes legal-footer field 11 into `Seller.lutArn`; `lutArnOf` takes the non-space token after `ARN` (optional `:`, `#` or `-`) or the trimmed whole footer. There is no required/year/format validation for the ARN. `BillingDocument.exemption` is `string[] | null`; an invoice-time non-India country prints `EXPORT_DECLARATION` (“Export of services without payment of tax under LUT”) plus a separate `LUT ARN: …` line. Missing ARN prints the Meteroid-legal-footer placeholder (B24), not a refusal. `GST_LUT_REFERENCE`, `exportMention` and `billing-sync-customers.ts` are removed; saving details sends only the declaration to the customer, not the ARN (`web/lib/billing/details.ts` `EXPORT_DECLARATION`, `meteroidCustomerPatch`; `web/lib/billing/meteroid.ts` `defaultInvoicingEntity`, `lutArnOf`; `web/lib/billing/documents.ts` `billingDocument`, `linesAndTotals`). `documentOf` supplies that seller and local Razorpay payment methods; the PDF module has `SAC` 998314 and `BillingDocument.seller`, not a fixed `SELLER`. The current/cached seller also sets PDF author metadata, not the billing email sender/reply-to. Setup reads the default invoicing entity first and stops on a failed read. A present GSTIN leaves the entity unchanged, even if its name is missing; without a GSTIN it seeds that same entity ID, not a first customer's entity (`web/scripts/meteroid-billing-setup.ts` entity step; `web/lib/billing/meteroid.ts` `defaultInvoicingEntity`). The app invoice is the tax invoice. Recipients still come from current billing emails. `keptPdf` reuses S3 bytes when the caller's row has the key and S3 is configured, without a document JSON/seller read. With S3 and a null caller key, it takes a per-invoice/document advisory transaction lock, rereads the stored key and reads the winner's object if present. Only a still-null key draws, uploads and saves the key in that transaction (timeout and max wait: 60 seconds). Without S3 it draws every time. First invoice and receipt draws fetch JSON separately; paid mail makes zero, one or two document reads depending on saved keys. No Meteroid PDF or readiness polling is used. A download or failed send can create the first kept copy before email completion; later seller/LUT/payment edits do not change it. S3/JSON/seller/render/key-save failures throw before sending and leave the marker null; a saved-object read failure never falls back to redrawing. Concurrent/stale-null-key callers wait for the first draw and reuse its bytes, resolving B25. An upload followed by DB rollback can leave an unreferenced object; a saved key whose S3 read fails is not repaired here. Retention/storage configuration belongs to [Billing code](billing-code.md#emails-and-pdfs) (`web/lib/billing/billing.ts` `keptPdf`; `web/lib/s3.ts` `s3Configured`, `getObjectBytes`, `putObject`). Upgrade-cancelled mail has no PDF and does not need seller details (`web/lib/billing/meteroid.ts` `sellerDetails`, `meteroidGrpc`, `decodeProto`; `web/lib/billing/documents.ts` `SAC`, `BillingDocument`, `sheet`, `finish`; `web/scripts/meteroid-billing-setup.ts` entity step). Ordinary send failure also throws and leaves the marker null. Missing RESEND_API_KEY is nevertheless recorded as completed; provider success followed by local save failure can duplicate beyond 24 hours. Daily repair waits 10 minutes for issued/paid workflow claims. It also retries overdue renewals with missing paused mail and finishes void-upgrade cancellation/email when overdueAt is set. Each overdue repair catches its own error. Missed reminders are best effort and never sent on a later day. See [Billing code — Mismatches](billing-code.md#mismatches) (`web/lib/billing/billing.ts` `documentOf`, `invoicePdf`, `receiptPdf`, `emailOnce`, `syncOrgInvoices`; `web/lib/billing/documents.ts` `billingDocument`, `renderInvoice`, `renderReceipt`).

A paid pack also produces the existing orgCredits email to the admin after Meteroid's PAID grant → wallet.funded → sync → announce. It is separate from the paid receipt, keyed `org-credits:<grantId>`, and still uses the shared default sender, not billing@ (`web/app/api/meteroid/webhook/route.ts` POST; `web/workflows/sync-org-credits.ts` `syncOrgCredits`; `web/lib/org-credits-email.ts` `announceNewGrants`; `web/lib/email.ts` `sendOrgCreditsEmail`). Meteroid's own customer emails must be disabled outside this app; setup does not disable them (`web/scripts/meteroid-billing-setup.ts` header).

### Workflows, retries and progress

`runAndWait` waits for a started workflow's return value (100 ms polling default). Only startup failure calls the same direct helper. People/assignment/credit write steps and queue step have maxRetries=0; AppErrors (including PeopleError/MinutesError) return `{ok:false,status,error,code}` through refusedOf; orThrow rebuilds the same AppError at the caller. REST uses errorResponse and tRPC adds data.refusal; other errors propagate. A failed started workflow is not rerun inline (`web/lib/workflow-runs.ts`; `web/workflows/steps/learners.ts`).

`queueEmails` starts deliverEmails; empty batch returns zero counts. Started batch returns emailFailures=0, emailsQueued=N and org-signed progress token, not delivery proof. Startup failure sends inline in parallel using each original event key and counts failures. `deliverEmail` (REST) tries inline first so the response can report emailSent; failure queues deliverEmails with the same key and still returns sent=false. Both direct-send paths are allowed by People rule 12; failed retry startup is logged, not a guaranteed delivery (`web/lib/queue-emails.ts` `queueEmails`, `deliverEmail`; `web/lib/send-email-now.ts`).

`deliverEmails` awaits messages in input order. Each sendOne step has maxRetries=4 and key = event key or step ID. Missing Resend key or a returned numeric HTTP 4xx other than 429 throws FatalError (no step retry). 429, 5xx, network exceptions and failures without a status throw an ordinary error for up to four retries. Fatal/exhausted failure writes failed progress and continues; finish writes done and closes stream (`web/workflows/send-emails.ts`; `web/workflows/steps/send-emails.ts`).

Progress token is run ID plus HMAC-SHA256 signature over org/run with BETTER_AUTH_SECRET. GET `/api/runs/:token` requires studio, returns 404 for invalid/other-org/missing run, streams no-store NDJSON. `followEmailProgress` buffers lines and shows sent/failed/background toasts; it does not undo the action (`web/lib/run-progress.ts`; `web/app/api/runs/[token]/route.ts`; `web/lib/follow-email-progress.ts`).

`sendEmail` loads Resend key at module initialization. Missing key warns and returns success:false (except development OTP); provider errors log and return success:false with error and status=result.error.statusCode; caught exceptions have an error message but no status. Before calling Resend, subjects replace each run of CR/LF with a space and trim it, for every template, including billing/OTP/issues. Default sender `RESEND_FROM_EMAIL` or TrainerTwin <no-reply@trainertwin.com>, reply-to support@trainertwin.com, optional CC, explicit sender override and optional nonempty PDF attachments (`SendEmailOptions`, `sendEmail`). Billing overrides the sender through `sendBillingEmail`. No bounce/inbox handler (`web/lib/email.ts`).

## Rules

1. Normal additions are immediate memberships, no invitation acceptance. HTTP Better Auth member/invitation routes are not_found/404; server invite/add/remove/update-role hooks give member_action_closed/403 for every role. Server leave is still unhooked (see [Auth — Mismatches](auth.md#mismatches)) (`web/app/api/auth/[...all]/route.ts` `open`; `web/lib/auth.ts` `organizationHooks`; `web/lib/invite/org.ts`).
2. Each new membership/assignment or successful learner grant produces one combined person email, not one message per part. Existing/skipped access produces none; common-link join produces none (`web/lib/invite/{org,twin,roleplay,credits}.ts`).
3. Assignment ownership uses user/member ID only; staff and disabled recipients are refused by addPeopleToOrg. Same role is preserved for existing members (`web/lib/org-people.ts`; `web/lib/assignments.ts`; `web/lib/twin-access.ts`).
4. Starting grants default to 30, once per org/email prior-grant history, **only for learner memberships added by this call**. Checks, starting credits, accounts and members commit together; short funds or a DB failure rolls back the whole add batch. Later assignment/email failures do not undo the committed add (`web/lib/org-people.ts:139–169`; `web/lib/minutes.ts` `giveStartingMinutes`).
5. Email failures leave memberships, access and credits intact and surface through immediate flags, queued progress or logs. Resend keys deduplicate only within the provider's 24-hour window (`web/lib/email.ts`; `web/lib/queue-emails.ts`).
6. Pending role-play resend intentionally creates a new email event while preserving code/date (`web/lib/invite/roleplay.ts`). REST immediate sends and workflow-startup fallback preserve the original event key, as allowed by People rule 12 (`web/lib/queue-emails.ts` `deliverEmail`, `queueEmails`).
7. Org grant announcement excludes known/nonpositive grants; existing migration-time grants are marked known. No admin/missing Resend still consumes announcement IDs (`web/lib/org-credits-email.ts`; people-first migration).
8. Shared sendEmail sends a one-line subject: CR/LF runs become spaces and outside whitespace is trimmed. sendOne stops permanently rejected 4xx (except 429) and missing-key sends without retry; returned 429/5xx and statusless failures are retryable. This classification is in the person-email workflow, not every direct sender (Mismatches) (`web/lib/email.ts:44–67`; `web/workflows/steps/send-emails.ts:20–31`).
9. Billing uses one invoice/event completion marker and key, with issued/reminder/paused invoice PDF and paid receipt-plus-invoice attachments; cancelled has none. Issued/reminder/paused add the saved Razorpay payment URL when locally unpaid; without one they ask for a reply to get a link, never print bank details. Kept PDFs read S3 bytes without Meteroid; missing ARN permits a placeholder, while S3 failure leaves mail incomplete. It sends to billing emails or enabled admin, not learners unless that address was explicitly entered as a billing recipient (`web/lib/billing/billing.ts` `recipients`, `documentOf`, `keptPdf`, `emailOnce`; `web/lib/billing/meteroid.ts` `sellerDetails`; `web/lib/razorpay.ts` `env`, `call`; `web/workflows/invoice-issued.ts` `invoiceIssued`; `web/lib/billing/billing.ts` `syncOrgInvoices`; `web/lib/email.ts` `billingEmail`, `sendBillingEmail`; [Billing code](billing-code.md)).

## Edge cases and limits

- People/assignment batches are atomic through addPeopleToOrg.then, but there is no action/email outbox transaction: failure after commit can leave state without its email payload. Write steps do not retry (`web/lib/org-people.ts:141–173`; `web/lib/invite/{twin,roleplay}.ts`; `web/workflows/steps/learners.ts`).
- Org announcement pushes IDs only after the whole loop. A later failure retries earlier sends using the same grant keys; absent admin/missing key loses notifications instead of deferring them (`web/lib/org-credits-email.ts`).
- Explicit twin-until formatting subtracts twelve hours and formats UTC; correct only UTC−11 through UTC+12 because assigner time zone is not saved (`web/lib/invite/person-email.ts` `lastDay`, shortcut comment).
- Common-link page opening commits joining before its minute check or any later call validation; abandoning prejoin or a failed call does not undo it. Assignment concurrency is DB-unique but ordinary twin/role-play writes lack conflict recovery, unlike common-link joining (`web/lib/pages/learner.ts` `loadSharedSession`; `web/lib/twin-access.ts` `twinAccessByCode`; `web/lib/invite/roleplay.ts`).
