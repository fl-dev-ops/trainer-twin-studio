# Billing code

> Billing links an org to Meteroid invoices, a Paid subscription and minute packs. Phase 3 adds Razorpay payment links and automatic payment recording; staff still record bank transfers in Meteroid. The app keeps invoice/payment copies, sends invoices and receipts, and blocks new voice calls and learner grants while paused. This is a **module spec**, describing the code, not the agreed rules in [Billing](billing.md). Owners: `web/lib/billing/{billing,meteroid,razorpay,documents}.ts` and the two invoice workflows. [Credits](credits.md) owns balances and spending; [Payments](payments.md) owns retained phase 1 purchases, which share the Razorpay switch and webhook.

## Who uses it

| Actor | What the code allows / pointer |
| --- | --- |
| Org admin / team | Read Billing, save details, request an upgrade, buy packs and download their org's PDFs (`web/lib/billing/trpc.ts` `billingRouter`; PDF routes below). |
| Learner | No billing procedures or PDF access (403). New voice calls are refused while paused; resumed live calls continue (`web/lib/trpc.ts` `studioProcedure`; `web/lib/interview-sessions.ts` `activateSession`). |
| TrainerTwin staff | Set the next-upgrade price with `web/scripts/billing-price.ts`; configure a tenant with `meteroid-billing-setup.ts`; reapply saved customer details/tax wording with `billing-sync-customers.ts`; check invariants with `check-billing.ts`; export payment fees with `billing-fee-report.ts`. Staff mark bank transfers paid and change/cancel existing subscriptions in Meteroid; duplicate card payments need a manual Razorpay refund and Meteroid credit note ([Billing](billing.md) rule 34). |
| Meteroid | Issues/numbers/calculates invoices, supplies invoice JSON, renews subscriptions, records payment, grants paid top-up credits and sends signed events (`web/lib/billing/meteroid.ts` `createPaidSubscription`, `createPackInvoice`, `getInvoiceRaw`; webhook POST). |
| Workflow / cron | Run invoice steps and repair copies/effects left behind (`web/workflows/invoice-issued.ts` `invoiceIssued`; `invoice-paid.ts` `invoicePaid`; `web/lib/billing/billing.ts` `checkAllBilling`). |
| Payer / Razorpay | Payer uses the hosted payment link. Razorpay collects money and supplies payment/fee data, not the tax invoice or billing emails (`web/lib/razorpay.ts` `createInvoicePaymentLink`, `fetchPayment`; `web/app/api/razorpay/webhook/route.ts` POST). |

## Data

### Org billing

`web/prisma/schema.prisma` `OrgBilling` owns both credit cache and billing state. Credit cache fields are described in [Credits](credits.md#data).

| Billing fields | Values and writers |
| --- | --- |
| `orgId`, `meteroidCustomerId` | Primary org ID, unique customer ID. Provisioning writes them (`web/lib/org-billing-setup.ts` `linkOrgToMeteroid`). |
| `plan` | String, defaults to `trial`; `invoicePaid` sets `paid`, `paidSubscriptionEnded` sets `trial`. |
| `paidSubscriptionId` | Nullable, unique. Set by `requestUpgrade`, early-webhook recognition in `kindOf`, or lost-ID adoption in `invoicePaid`; cleared by overdue-upgrade cancellation / `paidSubscriptionEnded`. |
| `paidMonthlyCents` | Nullable custom tax-inclusive USD monthly price; null displays $300 and uses Meteroid's plan price. `web/scripts/billing-price.ts` writes only this app field. Existing Paid subscriptions require a separate Meteroid price edit. |
| `pausedAt` | Nullable timestamp. `pauseFor` sets it only for the current subscription of an unpaused Paid org; renewal `invoicePaid` and `syncOrgInvoices` clear it when no current-subscription renewal copy is overdue unpaid; `paidSubscriptionEnded` always clears it. |
| `billingDetails` | Nullable JSON: `legalName`, `country`, `line1`, optional `line2`, `city`, `postalCode`, India-only `state` GST code, optional `taxId`, `emails`, required `phone` on new saves. Older JSON may have no phone. `saveBillingDetails` writes validated details after the Meteroid patch. |

The migration `web/prisma/migrations/20261112120000_billing_phase2/migration.sql` adds these fields; existing rows become Trial, without changing Meteroid subscriptions. SQL checks allow only trial/paid, positive-or-null custom cents, and a pause only on Paid. SQL does **not** require a Paid subscription ID or an overdue invoice; the check script checks those separately. Deleting the organization cascades billing and invoices (`OrgBilling`, `BillingInvoice` schema relations).

### Invoice copy

`web/prisma/schema.prisma` `BillingInvoice`; writers below are in `web/lib/billing/billing.ts`.

| Fields | Meaning / writer |
| --- | --- |
| `id`, `orgId`, `number` | Meteroid invoice ID (primary key), billed org FK, invoice number. `recordInvoice` creates the copy; invoice numbers are not DB-unique. |
| `kind`, `status` | Kind above; stored status `unpaid`, `paid` or `void`. Kind stays fixed once created. `recordInvoice`, `invoiceVoided`, `invoiceOverdue` update status. |
| `totalCents`, `taxCents`, `currency`, `credits`, `subscriptionId` | Meteroid total/tax/currency, pack credits (0 otherwise), nullable subscription ID (`recordInvoice`). |
| `issuedAt`, `dueDate`, `periodStart`, `periodEnd`, `paidAt`, `paymentRefs` | Issue timestamp; UTC date-only due/period fields; nullable paid timestamp; settled non-refund payment references (`recordInvoice`; `meteroid.ts` `toInvoice`). Missing paid time falls back to previous paid time or now. |
| `issuedRunAt`, `paidRunAt` | Workflow claims. `claim` sets them; a failed start resets that claim. They are not workflow run IDs. |
| `issuedEmailAt`, `reminderAt`, `overdueEmailAt`, `paidEmailAt` | Email completion markers (`emailOnce`). Paused and upgrade-cancelled share `overdueEmailAt`, since kind is fixed. |
| `overdueAt` | First overdue-handling timestamp (`invoiceOverdue`), set before pausing or voiding. A void upgrade with this marker resumes cancellation on retry. The daily overdue query uses `overdueEmailAt = null`, not a null `overdueAt` (`syncOrgInvoices`). |
| `paymentLinkId`, `paymentLinkUrl` | Nullable Razorpay link ID (unique) and hosted URL. `web/lib/billing/razorpay.ts` `ensurePaymentLink` saves them once when the ID is null; cancellation keeps them for history. |
| `razorpayPaymentId` | Nullable, unique accepted Razorpay payment ID. `razorpayInvoicePaid` saves it in the same local transaction as the remote mark attempt, or recovers it from a Meteroid transaction reference. | `createdAt`, `updatedAt` | DB/default and Prisma timestamps. |

SQL enforces positive totals, nonnegative credits, allowed kinds/statuses and an FK to `OrgBilling`, with cascade deletion. Indexes: `(orgId, issuedAt)` and `(status, dueDate)`. Currency, tax cents, paid-date/status agreement and subscription ownership are not SQL checks (migration above).

### Razorpay payment copy

`web/prisma/schema.prisma` `BillingPayment` and additive migration `web/prisma/migrations/20261113120000_billing_razorpay/migration.sql` add one row per accepted or duplicate invoice payment, separate from phase 1's `CreditPurchase`.

| Fields | Meaning / writer |
| --- | --- |
| `id`, `invoiceId`, `orgId`, `paymentLinkId` | Razorpay payment ID (primary key), Meteroid invoice ID (FK), copied org and link IDs. `web/lib/billing/razorpay.ts` `recordPayment` upserts by payment ID. Only `invoiceId` is an FK. |
| `status`, `amount`, `currency` | `applied` or `duplicate`; positive amount in the payment currency's subunits; exact invoice currency. Unknown links or wrong money produce no row (`razorpayInvoicePaid`). |
| `amountInr`, `feeInr`, `taxInr`, `method`, `international` | Nullable payment API data: INR conversion, fee and GST on the fee in paise, method and international flag. `recordPayment` reads it best-effort; `billing-fee-report.ts` refreshes some missing data. |
| `paidAt`, `createdAt` | Razorpay `created_at` timestamp, or now if its payment GET fails; DB creation time. `recordPayment` retries overwrite `paidAt` and other data, not append history. |

SQL checks status and positive amount, indexes `(orgId, paidAt)` and `paidAt`, and cascades payment deletion with the invoice. It does not check currency, INR amounts, copied org/link ownership or whether an applied payment's invoice is paid. The migration also adds unique nullable link/payment IDs on `BillingInvoice` (migration above).

## How it works

### Details and tax

1. `saveBillingDetails` parses before any billing change. Invalid data returns `BillingError` 400 with the first field path/problem. Unknown fields are rejected by `.strict()`. Strings are trimmed; country/tax ID uppercased; emails lowercased and deduplicated. Legal name/street are 1–200 characters, line2 at most 200, city 1–100, postal code 1–20, tax ID at most 50, email at most 320, 1–5 email entries before deduplication. Countries use `Intl.DisplayNames` with reserved/noncountry exclusions. Phone is required even with Razorpay off: remove spaces, hyphens, parentheses and dots, then require `+`, a nonzero first digit and 8–15 digits total (`web/lib/billing/details.ts:61–88` `billingDetailsInput`, `countryName`).
2. India requires a listed GST state code (retired 25/28 absent). An optional GSTIN must match the 15-character pattern, pass its mod-36 checksum and match the state's first two digits. A non-India state is refused (`billingDetailsInput`, `gstinChecksumOk`).
3. `locked` serializes details, upgrades and pack requests with a PostgreSQL org advisory transaction lock, timeout 60 seconds / max wait 30 seconds. The Meteroid customer PATCH runs **before** the local update. External failure rolls back the app update; there is no shared transaction with Meteroid (`billing.ts` `locked`, `saveBillingDetails`, `viaMeteroid`).
4. `meteroidCustomerPatch` sends name, address, tax ID, phone, first billing email plus all invoicing emails, custom taxes and export exemption. India prints `State name (code)` on line2, appended to the entered line2, and also sends the state field. Tamil Nadu (33) gets CGST 9% + SGST 9%; other India IGST 18%; outside India no tax and LUT exemption wording, with `GST_LUT_REFERENCE` if supplied (`details.ts` `addressLine2`, `taxFor`, `exportMention`, `meteroidCustomerPatch`). Meteroid applies the customer's tax when issuing invoices; invoice copies keep Meteroid's amounts (`billing.ts` `recordInvoice`).

### Upgrade and cancellation

1. `requestUpgrade` requires billing (404 if absent), Trial (Paid returns 409), then details (400). An existing Paid subscription ID reuses that subscription without a new request. The final result also includes nullable `payUrl` (`web/lib/billing/billing.ts:110–132` `requestUpgrade`).
2. It finds the active Meteroid plan named `Paid`, uses its first price component, and creates a manual-collection subscription starting on today's UTC date, activation `ON_START`, net terms 2 days. Optional custom cents override the monthly rate in USD. The key is `paid-subscription-<org>-<UTC day>-<count of all upgrade copies>`. Allowed response states are ACTIVE / PENDING_ACTIVATION / PENDING_CHARGE; another state returns 409 (`meteroid.ts` `paidPlan`, `createPaidSubscription`; `billing.ts` `requestUpgrade`).
3. Save its ID; keep the app on Trial. Try `syncOrgInvoices` immediately so the first invoice appears without waiting for the webhook. Sync failure is logged, not returned as an upgrade failure. Find the matching unpaid upgrade copy and call `payLinkQuietly`; return `{subscriptionId, created, payUrl}`. Missing copy, missing phone, Razorpay off or link failure gives null; the page falls back to the invoice email. A non-null URL redirects this tab to Razorpay (`billing.ts:127–141` `requestUpgrade`, `payLinkQuietly`; `billing-section.tsx:131–142` `PlanCard.upgrade`). Meteroid owns monthly renewal anchored to the subscription's requested start date.
4. `invoicePaid` refreshes payment first. It activates Paid when the stored subscription matches, or when the stored ID is null and Meteroid says the invoice's subscription is ACTIVE / PENDING_ACTIVATION / PENDING_CHARGE. A different stored ID, or a cancelled subscription with no stored ID, leaves the plan unchanged, logs for staff and emails “We'll be in touch about your plan.” Matching IDs bypass the live-status check (B14 below). No plan credits are granted.
5. At overdue time, `invoiceOverdue` refreshes Meteroid first. Set `overdueAt` before voiding an unpaid upgrade by gRPC, then set the copy void and cancel its subscription effective today by REST. A failed void re-reads payment: PAID means no cancellation. Cancellation errors are tolerated only if the subscription is already CANCELLED / COMPLETED / ABORTED. Clear the matching Trial subscription ID and send upgrade-cancelled email. A void upgrade with `overdueAt` continues from cancellation on retry; failed cancellation/email is also retried by the daily check. Other void invoices stop.
6. Signed cancelled/ended events resolve by subscription ID **before** any customer/org lookup, clear the matching Paid subscription ID, set Trial and clear pause. The daily check also reads a stored subscription's status and applies this effect for CANCELLED / COMPLETED / ABORTED. There is no customer cancel button (`paidSubscriptionEnded`, `syncOrgInvoices`; webhook POST; `billing-section.tsx` `PlanCard`).

### Buy packs

`buyPacks` accepts whole packs 1–10. Details must exist (400); the plan must be Paid and not paused (409, with separate messages). `packPrice` calculates the net cents near `floor(gross × 10000 / (10000 + total tax bp))`: try ±5 net cents, round each tax half upward separately, choose the closest total not above $25 × packs, at most one cent short. Divide net dollars by credits and give Meteroid an 8-decimal unit price; assert that it rounds back to net cents (`web/lib/billing/pricing.ts` `packPrice`, `totalWithTax`).

POST the Meteroid top-up with `amount = packs × 100`, `MINS`, `collection: SEND_INVOICE`, the net unit price and expiry at 23:59:59 UTC on request day +365 days. Key: `pack-<org>-<requestId>`. Read/store the invoice afterward and request its payment link through `payLinkQuietly`; return `{invoiceId, number, totalCents, payUrl}`. Read failure is logged and returns its ID with null number/total/URL. Link failure gives null URL without undoing the pack invoice. A non-null URL redirects this tab to Razorpay (`billing.ts:152–170` `buyPacks`, `packExpiry`; `meteroid.ts` `createPackInvoice`; `billing-section.tsx:341–353` `PacksCard.buy`). The tRPC input requires a UUID. `PacksCard` keeps one UUID for the selected quantity: an error retry reuses it, a quantity change or successful response generates a new one. It is component state, not persisted across reloads (`billing-section.tsx` `PacksCard`).

The pack-creation function does not grant credits or mark paid. A validated Razorpay payment marks the invoice paid through the shared handler below; bank transfers are still marked by staff. Meteroid grants PAID credits after payment; `wallet.funded` schedules `syncOrgCredits`, which refreshes the balance/grants and announces new grants to the admin. The paid invoice email and that credit-added email are separate. See [Credits](credits.md#how-it-works) (`web/app/api/meteroid/webhook/route.ts` POST; `web/lib/schedule-org-credits.ts` `scheduleOrgSync`; `web/workflows/sync-org-credits.ts` `syncOrgCredits`).

### Copy invoices and claim workflows

`syncInvoice` GETs the invoice, resolves its customer to an org unless an org was supplied, then calls `recordInvoice` and `startInvoiceWorkflows`. A first-seen nonpositive, DRAFT or VOID invoice is ignored. `UNCOLLECTIBLE` maps to void; PAID maps to paid; partial/processing/errored payment maps to unpaid. A paid/void copy cannot regress to unpaid, but paid and void can replace each other. Existing copies update amounts/dates/references, not kind/org (`billing.ts` `recordInvoice`, `statusOf`).

For early upgrade webhooks, `kindOf` can recognize a Paid-plan subscription while Trial has no stored ID and set that ID, but only when Meteroid reports ACTIVE / PENDING_ACTIVATION / PENDING_CHARGE. Otherwise matching current subscription + Trial means upgrade, matching + Paid means renewal, nonmatching subscription means other. No-subscription packs use the exact Meteroid line name `Purchase credits` (`billing.ts` `kindOf`; `meteroid.ts` `toInvoice`).

Atomic claims precede workflow startup. Non-void invoices claim issued once; paid invoices claim paid once. The `invoice.paid` webhook passes a paid hint even when the API still returns unpaid, so the paid workflow starts then too. Startup failure logs and clears the claim; a started-but-dead workflow retains its claim for daily repair (`billing.ts` `claim`, `startInvoiceWorkflows`).

### Invoice timers, payment, pause and resume

- `invoiceIssued` refreshes, returns immediately if void, tries the `payLink` step when unpaid, then sends the issued email. A link-step failure is caught so bank-transfer mail can still go out; daily repair retries missing links (`web/workflows/invoice-issued.ts:17–24`; `web/workflows/steps/billing.ts:18–22` `payLink`). Pack/other stop there. Renewal sleeps to 00:00 UTC the day before due and calls `invoiceReminder`, then sleeps to overdue time. Upgrade only sleeps to overdue time. Past times cause no sleep. Reminder refreshes, requires renewal/unpaid and the exact UTC day before due. Overdue handling refreshes and requires overdue plus unpaid, or a void upgrade with an existing overdue marker (`web/workflows/invoice-issued.ts` `invoiceIssued`, `until`; `web/lib/billing/billing.ts` `invoiceReminder`, `invoiceOverdue`).
- Overdue renewal writes `overdueAt` and pauses only a matching current subscription on Paid. Re-read Meteroid **after** the pause; if paid meanwhile, call `invoicePaid` to undo the pause and process payment instead of sending paused mail. Otherwise send the pause email only if the org is still paused on that subscription. No invoice kind other than renewal pauses (`billing.ts` `pauseFor`, `invoiceOverdue`).
- `invoicePaid` workflow makes **12 checks**, each calling `handlePaid` (which refreshes Meteroid), with a 10-second sleep after each unpaid check. PAID stops the loop. If all checks remain unpaid it returns `not_paid`; later daily checks can repair it. This covers Meteroid sending invoice.paid before its GET API shows PAID (`web/workflows/invoice-paid.ts` `invoicePaid`; `web/workflows/steps/billing.ts` `handlePaid`).
- The library `invoicePaid` applies the effect **before** sending email: upgrade activates Paid under the subscription guard above; renewal counts only the org's **current subscription's** other unpaid overdue renewal copies and clears pause if none remain. Old renewals neither block current unpause nor allow unpause while a current renewal is overdue. Renewal email outcome comes from `pausedAt` after the update: active, or still paused until the other overdue invoice is paid. Pack reports credits being added by Meteroid; other has no plan effect. Repetition re-applies these effects and checks the email marker (`billing.ts` `invoicePaid`).
- New voice calls read only `pausedAt` and return `MinutesError` 403 before closing other learner calls or reading call balances. Studio: “Your organization's plan is paused because an invoice is overdue. Pay it to continue (Settings › Billing).” Learner: “Practice is paused for this organization right now. Please ask your trainer.” Live resume returns before this check; pause does not change existing allowances or remove credits. Staff chat is unaffected (`web/lib/billing/paused.ts` `pausedReason`; `web/lib/interview-sessions.ts` `activateSession`; [Sessions](sessions.md)).
- Learner grants call `refuseWhenPaused` before writing. Starting grants only check if somebody actually needs a first grant; no-op/fully skipped batches can succeed. People additions run starting grants before account/member creation, so ordinary new learners are refused while team/admin additions do not use this check (`web/lib/minutes.ts` `grantMinutes`, `giveStartingMinutes`, `grantMinutesToMany`, `refuseWhenPaused`; `web/lib/org-people.ts` `addPeopleToOrg`; [Credits](credits.md)).

### Emails and PDFs

`emailOnce` reads the invoice's event marker. Billing recipients are the current details' emails or the enabled admin; no recipient logs and returns false. Issued/reminder/paused/paid render the app's invoice PDF; paid also renders its receipt. Each rendering reads Meteroid's invoice JSON, so paid mail makes two JSON reads (invoice first, receipt second), not one shared read. There is no PDF-readiness polling or Meteroid PDF download. A JSON read/render failure throws before sending and leaves the marker null for step retry. Send via Resend with `billing-<event>-<invoice id>`, then save the marker. Ordinary send failure throws. Missing `RESEND_API_KEY` is treated as completion even though sending was skipped (`billing.ts` `recipients`, `documentOf`, `invoicePdf`, `receiptPdf`, `emailOnce`; `web/lib/email.ts` `sendBillingEmail`, `sendEmail`).

| Event | Attachment / saved field |
| --- | --- |
| issued (all non-void kinds) | `<number>.pdf` / `issuedEmailAt` |
| reminder (unpaid renewal, due-tomorrow day only) | `<number>.pdf` / `reminderAt` |
| paused (current renewal) | `<number>.pdf` / `overdueEmailAt` |
| upgrade_cancelled | None / `overdueEmailAt` |
| paid (all paid kinds) | `RCPT-<number>.pdf`, then `<number>.pdf` / `paidEmailAt` |

`emailOnce` supplies `payUrl = paymentLinkUrl` only for a locally unpaid row. Issued/reminder/paused HTML adds a “Pay <amount> now” button; plain text adds “Pay online: <URL>”. Configured bank instructions remain as “Or pay by bank transfer” beside the link; without a link the old instructions/attached-invoice fallback remains. Paid/cancelled templates have no payment button (`billing.ts:440–469` `emailOnce`; `web/lib/email.ts:406–458` `billingEmail`). `billingEmail` also builds escaped HTML and plain text, with Billing URL, amounts formatted in the invoice's currency by `pricing.ts` `formatMoney`, due date and payment outcome on paid. Default sender is `TrainerTwin Billing <billing@trainertwin.com>`, configurable by `BILLING_FROM_EMAIL`, reply-to support@trainertwin.com. Without instructions, copy points to the attached invoice. Full subjects/recipient boundaries: [People and emails](invites-and-emails.md#billing-emails) (`web/lib/email.ts` `billingEmail`, `sendBillingEmail`).

`documentOf(row)` reads `getInvoiceRaw(row.id)` and the org's name, then calls `billingDocument(raw, orgName)`. Both PDFs use `customer_details`, Meteroid's **invoice-time customer snapshot**, not today's app details or a fresh customer lookup. The snapshot supplies buyer name, address, email and tax ID; only a missing/empty customer name falls back to the current org name. India uses GSTIN and state/code for place of supply; the state suffix on address line2 is moved after city/postal code. Outside India uses Tax ID and “Outside India (export of services)” (`billing.ts` `documentOf`; `meteroid.ts` `RawInvoice`, `getInvoiceRaw`; `documents.ts` `billingDocument`).

`billingDocument` maps invoice number, issue/due dates, currency, subtotal, total, tax breakdown and every line. Line amounts are rounded from quantity × unit price; unit prices allow four decimals. `Purchase credits` becomes minute-pack wording, every line gets SAC 998314, and a period's exclusive end becomes its last covered day. Positive non-exempt taxes print their name/rate; the first exemption supplies its wording. Payment history includes only SETTLED non-refund transactions: reference, processed date and cents, labelled “Bank transfer” (`documents.ts` `billingDocument`, `describe`, `period`, `money`).

Both renderers take a `BillingDocument`, not billing details or a `BillingInvoice`. They draw one A4 page with title/numbers top left, TrainerTwin mark top right, seller/buyer side by side, amount, line table and totals. `SELLER` fixes Forever Learning Solutions Pvt Ltd's address, GSTIN 33AAGCF6592D1ZN, SAC 998314 and billing@trainertwin.com; the setup script uses the same constant. The **app's invoice PDF is the tax invoice** (`documents.ts` `SELLER`, `sheet`, `linesAndTotals`; `web/scripts/meteroid-billing-setup.ts` invoicing-entity step).

- `invoicePdf(row)` calls `renderInvoice(doc, paymentInstructions(), row.status === "unpaid" ? row.paymentLinkUrl : null)`: an unpaid copy with a URL prints “Pay online” and the URL with a clickable PDF link; bank instructions are labelled “Or by bank transfer” beside it (`billing.ts:427–428`; `documents.ts:275–302` `renderInvoice`, `Sheet.link`). Other content: invoice number, UTC issue/due dates, place of supply, amount due, optional multiline `BILLING_PAYMENT_INSTRUCTIONS` and quote-the-invoice reminder, lines, taxable value/tax/total/amount due, exemption wording and computer-generated/no-signature footer. It still shows the full amount due when attached to paid mail (`billing.ts` `invoicePdf`, `paymentInstructions`; `documents.ts` `renderInvoice`).
- `receiptPdf(row)` calls `renderReceipt(doc, row.paidAt ?? row.updatedAt)`: invoice number, `receiptNumber(number)` = `RCPT-<number>`, UTC date paid, place of supply, full amount paid, the same lines/totals and a payment-history table with method/reference/date/amount/receipt number. Without settled transactions, one bank-transfer row uses the full invoice total and that paid date. Its footer points to the invoice as the tax invoice (`billing.ts` `receiptPdf`; `documents.ts` `receiptNumber`, `renderReceipt`).

Amounts use the invoice currency. Fixed Helvetica fonts use WinAnsi: unsupported currency symbols (such as ₹) use a currency code instead (`money`), other unsupported characters become `?` (`safe`). Descriptions, exemption wording and payment instructions wrap at words; buyer fields and payment-history rows do not. Identical document/render inputs yield identical bytes: automatic metadata updates are off; creation/modification dates use the invoice issue day or receipt paid timestamp, never the render clock. Render inputs are read again, not saved with the emailed bytes (B15 below) (`documents.ts` `money`, `safe`, `Sheet.wrap`, `finish`, both renderers).

`orgInvoice` scopes downloads to the signed-in org (404 otherwise). Both PDFs are rendered live from Meteroid JSON; `viaMeteroid` maps a JSON read failure (including Meteroid 404) to 502. Receipt requires stored paid status (409 otherwise), checked before the JSON read. There is no 409 “PDF not ready” and no offline receipt. Routes require authentication (401), enabled studio membership (403 otherwise), PDF content type, attachment filename, private/no-store (`billing.ts` `invoicePdfFor`, `receiptPdfFor`, `viaMeteroid`; both invoice GET routes). UI download buttons use `fetch`, read the blob, click a temporary object-URL download and revoke it. The tab's `OrgPin` fetch wrapper sends its org header, unlike a plain anchor; non-OK responses toast the route error (`billing-section.tsx` `download`; `web/components/org-pin.tsx` `install`).

### Daily repairs and local UI

`checkAllBilling` visits every `OrgBilling`, isolates per-org errors and returns results. `syncOrgInvoices` does this (`billing.ts` `syncOrgInvoices`, `checkAllBilling`; `meteroid.ts` `listInvoices`):

1. Read the newest **50** Meteroid invoices, record them and start missing workflows. A claim is considered dead after **10 minutes** without its email (wall-clock `Date.now`, not the supplied simulated `now`). Directly handle missing paid effect/email first; otherwise missing issued email. These repair failures log and continue; record/start errors can still abort this org's pass.
2. Read **all local unpaid copies**, not only the recent 50. If a link ID exists, ask Razorpay and settle a paid link through `reconcilePaymentLink`; otherwise call `ensurePaymentLink`. Each failure logs and continues. The first Meteroid list still has to succeed before this loop can run (`billing.ts:508–517`).
3. Select local overdue upgrade/renewal copies with `overdueEmailAt = null`: unpaid rows, plus void upgrades whose `overdueAt` is non-null. Call `invoiceOverdue` for each in its own try/catch. This finishes partial upgrade cancellation and repairs missing paused mail even after `overdueAt` was written. One overdue failure does not stop later rows.
4. If paused, count unpaid overdue renewals of the **current subscription**. Clear pause if none remain (including when the overdue invoice was voided).
5. GET the stored Paid subscription, including a pending Trial subscription. CANCELLED / COMPLETED / ABORTED calls `paidSubscriptionEnded`: Trial, no ID, unpaused. This status-read failure can abort the org's result after earlier repairs.

No direct reminder repair runs. A newly restarted issued workflow still calls `invoiceReminder`, which sends only on the correct day; missed reminders are best effort, never sent later.

Vercel GET cron `/api/internal/billing/check` runs **daily at 00:15 UTC** (`web/vercel.json`). Route GET/POST accepts Bearer or x-internal-secret matching `CRON_SECRET`, falling back to `INTERNAL_API_SECRET`. No configured secret allows only off-Vercel execution; on Vercel it fails closed. Route limit is 300 seconds; per-org errors still return `{ok:true, orgs}` (`web/app/api/internal/billing/check/route.ts` `isAuthorized`, GET).

`billingOverview` reads only the app, newest 100 invoice copies, and supplies plan/details/prices, pending upgrade and latest matching unpaid/overdue renewal views. Each locally unpaid view carries `payUrl`, including overdue views; paid/void carry null (`billing.ts:580–605`). `InvoicesCard` adds Pay now to unpaid/overdue rows with a URL; `PlanCard` adds it to pending-upgrade and paused-renewal notices. These use `window.location.assign`, not an embedded checkout (`billing-section.tsx:58–60,159–174,408–410`). Return-page confirmation and polling are described below. On Paid, `renewsOn` is the largest `periodEnd` among non-void copies matching the current subscription, or null without a period. This is an invoice-derived date, not a live subscription lookup. Settings shows it beside the monthly price; details; packs only on Paid, with expiry copy “a year after the invoice date”; invoice statuses/download buttons and paid receipts. Paused pack purchase is disabled. URL `?tab=billing` selects the tab only for studio roles, otherwise Account. `BillingBanner` fetches its own overview key, stale time 5 minutes, retries off: pause alert first, otherwise **any current-subscription** unpaid renewal's due date (not only tomorrow). It has no polling interval (`web/lib/billing/billing.ts` `billingOverview`; `web/components/billing/billing-section.tsx` `BillingSection`, cards; `billing-banner.tsx` `BillingBanner`; `web/app/dash/settings/page.tsx` `SettingsPage`; `web/app/dash/layout.tsx` `DashLayout`).

### Razorpay: collecting invoice payments

#### Make and show a link

1. `ensurePaymentLink` returns null while off. Otherwise it reads the invoice and current billing details. A saved URL is returned first; without one, only an unpaid positive invoice with a phone qualifies. Missing phone logs and returns null. Saving a phone does not itself make links: a request/workflow/daily check must run afterward (`web/lib/billing/razorpay.ts:33–42`; `billing.ts:88–100,508–517`).
2. Create for exact `totalCents`/`currency`, description `TrainerTwin invoice <number>`, unique Razorpay reference = invoice ID, notes `invoiceId`/`invoiceNumber`/`orgId`, and today's legal name, first email and phone. Disable partial payment, email, SMS and reminders; omit expiry; use GET callback `<studioUrl>settings?tab=billing&paid=<encoded number>`. Currency follows the invoice, not a USD override (`web/lib/billing/razorpay.ts:25–26,43–53`; `web/lib/razorpay.ts:83–108` `createInvoicePaymentLink`).
3. Razorpay HTTP 400 on create triggers a reference lookup and reuses the existing link if found; other errors propagate. An ID-null conditional update saves ID/URL and rereads the winner's URL. Creation relies on Razorpay's unique reference, not an app lock (`web/lib/billing/razorpay.ts:54–61`; `web/lib/razorpay.ts:111–114` `paymentLinkByReference`).
4. Issued workflow tries the link before email; upgrade/pack handlers return `payUrl`. Overview/mail/PDF expose saved URLs while locally unpaid; buttons redirect to the hosted page, never collect card details in TrainerTwin. Link failure does not undo an invoice or hold up bank-transfer mail. Late-link email coverage is B20 (`web/workflows/invoice-issued.ts:19–23`; `billing.ts:127–141,166–170,427–428,464,592`; `billing-section.tsx:58–60,135,346`).

#### Webhook and settlement

POST `/api/razorpay/webhook` returns 404 while off and 401 for missing/bad HMAC. Signed `payment_link.paid` with truthy `notes.invoiceId` and a payment entity goes to `razorpayInvoicePaid`; lookup uses the saved **link ID**, not the note's invoice ID. Other paid links and `invoice.paid` retain phase 1 purchases. `refund.processed` uses only phase 1's log-only refund helper; phase 3 refunds/credit notes are manual (`web/app/api/razorpay/webhook/route.ts:26–59`; [Payments](payments.md#webhooks-and-refunds)).

`razorpayInvoicePaid` does this (`web/lib/billing/razorpay.ts:106–147`):

1. Unknown link or amount/currency unequal to the invoice logs and returns `ignored` before changing data. The webhook returns 200 `{ok:true,result}` for ignored/applied/duplicate outcomes. Other unexpected errors escape for retry; phase 1 `PurchaseError` is acknowledged 200. Signed JSON/entities are cast, not runtime-validated, so malformed signed bodies can throw (`razorpay.ts:107–115`; webhook `route.ts:33–59`).
2. Take a per-invoice PostgreSQL advisory transaction lock (`razorpay:<invoice id>`, timeout 60 seconds / max wait 30 seconds). Reread: same accepted `razorpayPaymentId` means applied retry; another saved ID means duplicate. Neither asks Meteroid to mark again (`razorpay.ts:116–123`).
3. With no accepted ID, read Meteroid JSON. A transaction with this payment reference recovers a successful remote mark whose local save was lost. Otherwise PAID or VOID means duplicate. For an unpaid invoice, write accepted ID and call `markInvoicePaid(id, (amount / 100).toFixed(2), paymentId)` within the local transaction. The ID commits only when the mark call and DB commit succeed. This stops concurrent webhook/confirm/daily calls from marking twice while Meteroid still reads UNPAID, but does not make the remote mark atomic with PostgreSQL (B16) (`razorpay.ts:124–137`; `web/lib/billing/meteroid.ts:62–64`).
4. **After** the transaction, GET the Razorpay payment best-effort and upsert `BillingPayment` as applied/duplicate. API failure saves null fee/method data and now as paid time. Duplicate logs its reason and refund instruction, then stops. Applied calls `syncInvoice` with a paid hint to claim the existing invoice-paid workflow despite a stale unpaid GET. That workflow polls Meteroid, activates Paid/unpauses and sends receipts; Meteroid grants pack credits (`razorpay.ts:80–98,139–147`; `billing.ts:231–237,258–263,349–383`; `web/workflows/invoice-paid.ts` `invoicePaid`).

`closePaymentLink` is called on handled bank payments, explicit invoice voids and overdue-upgrade cancellation. It skips off/no-link/accepted-Razorpay-ID rows, tries cancel, logs **all** errors and returns success to its caller. IDs/URLs stay stored. No durable cancellation marker/retry queue exists (B18) (`web/lib/billing/razorpay.ts:64–73`; `billing.ts:330,381,387–390`).

#### Return page and missed webhook

- `PaymentArriving` reads `paid` and `razorpay_payment_link_id`. It calls `billing.confirmPayment` once for a link ID and invalidates overview afterward. When the named invoice is not locally paid, it polls overview every **3 seconds for up to 2 minutes**, then shows taking-longer copy. Invoice-number matching is only UI state, not proof of payment (`web/components/billing/billing-section.tsx:67–105`).
- Studio-only `confirmPayment` accepts `plink_` plus alphanumeric characters and finds the link in the active org (404 otherwise). Paid/void returns local status. Unpaid asks Razorpay through `reconcilePaymentLink`, returning applied/duplicate/ignored or pending. Provider/DB failure logs and returns pending for webhook/daily repair (`web/lib/billing/trpc.ts:41–55`).
- `reconcilePaymentLink` checks off/no-link first, GETs the link and requires status `paid`. It chooses the first captured payment, falling back to the first listed payment, then hands its ID/amount and link currency to the **same** `razorpayInvoicePaid` handler. Daily sync repairs every local unpaid copy or makes its missing link. It does not enumerate all payments on already-paid invoices (B17) (`web/lib/billing/razorpay.ts:150–157`; `billing.ts:508–517`).

#### Fee report

From `web/`, `bun scripts/billing-fee-report.ts --month YYYY-MM > fees.csv` selects local `BillingPayment.paidAt` within the UTC month, oldest first, including duplicates. It refreshes and saves API data for payments missing fee or INR conversion. Settlement reconciliation reads batches of 1000 for the requested month **and next month**, joining settlement ID/date to payment entries. Failures silently leave blanks. CSV contains paid timestamp, payment ID, status, invoice, org slug, amount/currency, INR conversion, fee, GST on fee, calculated net, method, international flag, settlement ID/date. Monetary subunits divide by 100; net = `amountInr - feeInr` (code treats fee as including GST). Settlement metadata is joined at report time, not stored locally. CSV cells quote commas/quotes/newlines; stderr prints payment/duplicate counts. Month syntax is checked, not range 01–12; JavaScript dates normalize other values. Missing-field/settlement limits are B19 (`web/scripts/billing-fee-report.ts:12–64`; `web/lib/razorpay.ts:139–144` `settlementRecon`).

**Reported live evidence, 11 Nov 2026 — supplied with this task, not rerun here:** Razorpay test mode + Meteroid Sandbox accepted USD links; the hosted page asked for mobile/email again and offered cards only for USD. The payer returned to `settings?tab=billing&paid=<number>&razorpay_payment_link_id=…`; `confirmPayment` asked Razorpay. Daily repair recovered a lost webhook. Concurrent duplicate callbacks marked Meteroid once after the accepted-ID transaction fix. A bank-transfer payment cancelled its link. Payment GET supplied `base_amount`, `fee`, `tax` in INR paise. These attest happy paths, not production deployment, real settlements or the failure cases below.

### Lifecycles in words

- Plan: Trial → request → Trial with pending Paid subscription → upgrade payment → Paid → overdue current renewal → Paid paused → all current-subscription overdue renewals paid/void → Paid unpaused. Pending upgrade overdue → void + cancel → Trial without pending ID. Cancelled/ended current Paid subscription → Trial unpaused (`billing.ts` `requestUpgrade`, `invoiceOverdue`, `invoicePaid`, `paidSubscriptionEnded`).
- Invoice: unseen finalized positive invoice → unpaid copy → paid or void. Paid/void never → unpaid by a stale read. Pack/other can remain unpaid indefinitely without pause (`recordInvoice`, `invoiceOverdue`).
- Delivery: null claim → claimed timestamp → workflow started → email marker; startup failure → null claim; claimed >10 minutes without email → direct daily repair. Send failure leaves marker null; successful send (or missing Resend key) sets it (`claim`, `startInvoiceWorkflows`, `emailOnce`, `syncOrgInvoices`).

## Rules

1. All five billing tRPC procedures, including `confirmPayment`, require admin/team; learners are FORBIDDEN. PDF access is same-org studio only (`web/lib/billing/trpc.ts` `billingRouter`; `web/lib/trpc.ts` `studioProcedure`; PDF GET routes).
2. Invalid details return the first problem with 400 before any remote write; valid saves patch Meteroid before app JSON (`billing.ts` `saveBillingDetails`; `details.ts` `billingDetailsInput`). Unknown detail fields are rejected by `.strict()`.
3. Upgrade requires Trial plus details and reuses a stored pending subscription ID. Paid returns 409 (`billing.ts` `requestUpgrade`).
4. Whole packs 1–10 require details, Paid and no pause. Pack total cannot exceed nominal price and is at most one cent short for supported taxes (`billing.ts` `buyPacks`; `pricing.ts` `packPrice`).
5. Razorpay invoice payment handling calls Meteroid `markInvoicePaid`; upgrade/pack creation does not. Meteroid, not this app, grants the paid top-up credits (`web/lib/billing/razorpay.ts:106–147` `razorpayInvoicePaid`; `meteroid.ts` `markInvoicePaid`, `createPackInvoice`; `billing.ts` `invoicePaid`).
6. First-seen zero/draft/void invoices are ignored; DB rejects totals ≤0. Known kinds persist; stale reads cannot make paid/void unpaid (`billing.ts` `recordInvoice`; billing migration).
7. At most one issued and paid workflow claim wins concurrently per invoice. A failed start releases it (`billing.ts` `claim`, `startInvoiceWorkflows`).
8. Only unpaid renewals get reminders on the UTC day before due; only current Paid renewal copies can pause. Upgrade overdue voids/cancels, pack/other never pause (`invoiceReminder`, `invoiceOverdue`, `pauseFor`).
9. Call/grant refusal reads only local pause state; resumes bypass pause. No billing pause operation removes credit cache or ledger balances (`paused.ts` `pausedReason`; `interview-sessions.ts` `activateSession`; `minutes.ts` `refuseWhenPaused`; `billing.ts` `pauseFor`).
10. Paid renewal processing clears pause only when no other overdue unpaid renewal copy of the current subscription exists, and the email outcome reflects pause state after the update. Paid plan/effects happen before receipt email (`billing.ts` `invoicePaid`).
11. Billing event email uses its stored marker and Resend event key. Failed sends retain null markers, except missing Resend configuration. Paid emails attach receipt then invoice (`billing.ts` `emailOnce`; `web/lib/email.ts` `sendEmail`).
12. Signed Meteroid callbacks accept flat or `data` fields, with flat fields winning. Bad signature is 401; malformed JSON 400; unknown customers/types are acknowledged and ignored, except subscription ending resolves the stored subscription ID without requiring a customer. Invoice read errors propagate for Meteroid retry (`web/app/api/meteroid/webhook/route.ts` POST; `web/lib/meteroid.ts` `verifyWebhook`).
13. Invoice and receipt use the issued customer snapshot and the app's shared layout, never Meteroid's PDF. Same document/render inputs give identical bytes. Both downloads need live invoice JSON; read failure returns 502, not PDF-not-ready 409. Only a receipt whose stored status is not paid returns 409 (`documents.ts` `billingDocument`, `renderInvoice`, `renderReceipt`, `finish`; `billing.ts` `documentOf`, `invoicePdfFor`, `receiptPdfFor`).
14. Invoice links disable provider notifications/reminders and partial payment, use invoice ID as unique reference, and require a saved phone before creation (`web/lib/billing/razorpay.ts:33–61`; `web/lib/razorpay.ts:83–108`).
15. Unknown invoice links or money mismatch change nothing and return ignored 200. Accepted-ID retries do not mark again; different payments on an already accepted/paid/void invoice are recorded as duplicates and logged. Remote/local failure gaps are B16–B17 (`web/lib/billing/razorpay.ts:106–147`; `web/app/api/razorpay/webhook/route.ts:37–52`).
16. Return-URL parameters never mark paid by themselves: studio-only confirmation checks same-org ownership and asks Razorpay; failure gives pending (`web/lib/billing/trpc.ts:41–55`).
17. Daily Razorpay repair covers every **local unpaid** invoice after the Meteroid list succeeds. Paid/void cancellation and missing-payment record repair are not part of that loop (B17–B18) (`billing.ts:492–517`).

## Edge cases and limits

- External success and local DB failure are not atomic. Meteroid may keep updated details/a subscription/top-up despite rollback or lost response; error copy saying “Nothing was changed” refers imperfectly to that boundary (`billing.ts` `locked`, `viaMeteroid`, request functions).
- Upgrade keys contain today's date; retries across UTC midnight can use a new key after a remote success/local failure. Pack retries recompute expiry and tax from today's/current details; the same request key can get a different body later. The UI keeps its requestId after an error, but resets it on quantity change, success or remount; it is not a persisted retry ID (`billing.ts` `requestUpgrade`, `buyPacks`, `packExpiry`; `billing-section.tsx` `PacksCard.buy`).
- Kind depends on app plan when first seen. A much-delayed first-paid event with several subscription invoices can classify more than one as upgrade; old-subscription invoices first seen after cancellation become other (`billing.ts` `kindOf`, `recordInvoice`).
- Meteroid recent-invoice fetch is one page (50), UI one page (100); there is no pagination or local PDF storage. Razorpay repair scans all locally unpaid rows, not unseen Meteroid invoices outside that page. Reminder/overdue/payment steps refresh Meteroid, while call refusal and overview never do (`meteroid.ts` `listInvoices`; `billing.ts` `billingOverview`, `refreshed`, `invoicePdfFor`).
- Banner state has no five-second credit-version invalidation or regular polling; mutations in Billing invalidate its query prefix, but an external payment/pause may need a refetch/reload. Query errors hide the banner (`billing-banner.tsx` `BillingBanner`; `billing-section.tsx` mutations).
- Both PDFs preserve the invoice-time buyer snapshot; current billing emails still decide recipients. Unsupported scripts are replaced; only descriptions, exemption wording and instructions wrap. Long buyer fields, unbroken words/references, many lines/payments or long instructions can overflow the single page; there is no pagination. Neither PDF adds a second INR-conversion amount; current billing rules do not require one. Every payment-history method is “Bank transfer”; the receipt's headline/closing total is the full invoice total, not a sum/reconciliation of transactions (`billing.ts` `recipients`, `documentOf`; `documents.ts` `safe`, `Sheet.wrap`, `billingDocument`, both renderers).
- Setup dry-run performs reads, suppresses writes. It updates only the entity found on the first customer and does not disable Meteroid customer emails or set bank details/FX conversion. Its PUT price call is outside the shared wrapper's declared method union (`meteroid-billing-setup.ts:71`; `web/lib/meteroid.ts:28`). This is a type-contract issue, not a new REST feature.
