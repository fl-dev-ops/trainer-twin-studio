# Billing code

> Billing links an org to Meteroid invoices, a Paid subscription and minute packs. Phase 3 adds Razorpay payment links and automatic payment recording; staff can still record payments made outside Razorpay in Meteroid. The app keeps invoice/payment copies, sends invoices and receipts, and blocks new voice calls and learner grants while paused. This is a **module spec**, describing the code, not the agreed rules in [Billing](billing.md). Owners: `web/lib/billing/{billing,meteroid,razorpay,documents}.ts` and the two invoice workflows. [Credits](credits.md) owns balances and spending; [Payments](payments.md) owns retained phase 1 purchases, which share the always-on Razorpay API and webhook.

## Who uses it

| Actor | What the code allows / pointer |
| --- | --- |
| Org admin / team | Read Billing, save details, buy packs and download their org's PDFs. Contact TrainerTwin to move to a paid plan; no upgrade procedure or button exists (`web/lib/billing/trpc.ts` `billingRouter`; `web/components/billing/billing-page.tsx` `PlanSection`; PDF routes below). |
| Learner | No billing procedures or PDF access (403). New voice calls are refused while paused; resumed live calls continue (`web/lib/trpc.ts` `studioProcedure`; `web/lib/interview-sessions.ts` `activateSession`). |
| TrainerTwin staff | Create each org's own `CUSTOM` plan and manual-collection subscription in Meteroid, after its billing details are saved ([Billing](billing.md) rules 2, 6, 10). The app adopts its invoice; it does not create or select paid plans (`billing.ts` `kindOf`). Configure a tenant with `web/scripts/meteroid-billing-setup.ts`, check invariants with `check-billing.ts`, export payment fees with `billing-fee-report.ts`. Edit the company's name, address, GSTIN, contact email and LUT ARN in Meteroid Settings › Invoicing entity (`meteroid.ts` `sellerDetails`, `lutArnOf`); mark outside-Razorpay payments and change/cancel subscriptions there. Duplicate card payments need a manual Razorpay refund and Meteroid credit note (rule 34). |
| Meteroid | Issues/numbers/calculates invoices, supplies invoice JSON, renews subscriptions, records payment, grants paid top-up credits and sends signed events (`web/lib/billing/meteroid.ts` `getSubscription`, `createPackInvoice`, `getInvoiceRaw`; webhook POST). |
| Workflow / cron | Run invoice steps and repair copies/effects left behind (`web/workflows/invoice-issued.ts` `invoiceIssued`; `invoice-paid.ts` `invoicePaid`; `web/lib/billing/billing.ts` `checkAllBilling`). |
| Payer / Razorpay | Payer uses the hosted payment link. Razorpay collects money and supplies payment/fee data, not the tax invoice or billing emails (`web/lib/razorpay.ts` `createInvoicePaymentLink`, `fetchPayment`; `web/app/api/razorpay/webhook/route.ts` POST). |

## Data

### Org billing

`web/prisma/schema.prisma` `OrgBilling` owns both credit cache and billing state. Credit cache fields are described in [Credits](credits.md#data).

| Billing fields | Values and writers |
| --- | --- |
| `orgId`, `meteroidCustomerId` | Primary org ID, unique customer ID. Provisioning writes them (`web/lib/org-billing-setup.ts` `linkOrgToMeteroid`). |
| `plan` | String, defaults to `trial`; `invoicePaid` sets `paid`, `paidSubscriptionEnded` sets `trial`. |
| `paidSubscriptionId` | Nullable, unique. Set by invoice recognition in `kindOf` or lost-ID adoption in `invoicePaid`; cleared by overdue-upgrade cancellation / `paidSubscriptionEnded`. There is no app-side paid price field; staff keep prices on each org's Meteroid plan. |
| `pausedAt` | Nullable timestamp. `pauseFor` sets it only for the current subscription of an unpaused Paid org; renewal `invoicePaid` and `syncOrgInvoices` clear it when no current-subscription renewal copy is overdue unpaid; `paidSubscriptionEnded` always clears it. |
| `billingDetails` | Nullable JSON: `legalName`, `country`, `line1`, optional `line2`, `city`, `postalCode`, India-only `state` GST code, optional `taxId`, `emails`, required `phone` on new saves. Older JSON may have no phone. `saveBillingDetails` writes validated details after the Meteroid patch. |

The migration `web/prisma/migrations/20261112120000_billing_phase2/migration.sql` adds these fields; existing rows become Trial, without changing Meteroid subscriptions. SQL checks allow only trial/paid and a pause only on Paid. The removed `paidMonthlyCents` field and its positive-price check are not in the current schema/migration. SQL does **not** require a Paid subscription ID or an overdue invoice; the check script checks those separately. Deleting the organization cascades billing and invoices (`OrgBilling`, `BillingInvoice` schema relations).

| `kind`, `status` | Kind above; stored status `unpaid`, `paid` or `void`. Kind stays fixed once created. `recordInvoice`, `invoiceVoided`, `invoiceOverdue` update status. |
| `totalCents`, `taxCents`, `currency`, `credits`, `subscriptionId` | Meteroid total/tax/currency, pack credits (0 otherwise), nullable subscription ID (`recordInvoice`). |
| `issuedAt`, `dueDate`, `periodStart`, `periodEnd`, `paidAt`, `paymentRefs` | Issue timestamp; UTC date-only due/period fields; nullable paid timestamp; settled non-refund payment references (`recordInvoice`; `meteroid.ts` `toInvoice`). Missing paid time falls back to previous paid time or now. |
| `issuedRunAt`, `paidRunAt` | Workflow claims. `claim` sets them; a failed start resets that claim. They are not workflow run IDs. |
| `issuedEmailAt`, `reminderAt`, `overdueEmailAt`, `paidEmailAt` | Email completion markers (`emailOnce`). Paused and upgrade-cancelled share `overdueEmailAt`, since kind is fixed. |

| `paymentLinkId`, `paymentLinkUrl` | Nullable Razorpay link ID (unique) and hosted URL. `web/lib/billing/razorpay.ts` `ensurePaymentLink` saves them once when the ID is null; cancellation keeps them for history. |

| `invoicePdfKey`, `receiptPdfKey` | Nullable S3 keys for each first drawn PDF. `keptPdf` takes a per-document advisory transaction lock, rereads the key and, if still null, uploads before saving it in that transaction. `recordInvoice` does not clear them when amounts/status change. No DB check validates their path or S3 object. |
| `createdAt`, `updatedAt` | DB/default and Prisma timestamps. |

SQL enforces positive totals, nonnegative credits, allowed kinds/statuses and an FK to `OrgBilling`, with cascade deletion. Indexes: `(orgId, issuedAt)` and `(status, dueDate)`. Currency, tax cents, paid-date/status agreement and subscription ownership are not SQL checks (migration above).

### Razorpay payment copy

`web/prisma/schema.prisma` `BillingPayment` and additive migration `web/prisma/migrations/20261113120000_billing_razorpay/migration.sql` add one row per accepted or duplicate invoice payment, separate from phase 1's `CreditPurchase`.

| Fields | Meaning / writer |
| --- | --- |
| `id`, `invoiceId`, `orgId`, `paymentLinkId` | Razorpay payment ID (primary key), Meteroid invoice ID (FK), copied org and link IDs. `web/lib/billing/razorpay.ts` `recordPayment` upserts by payment ID. Only `invoiceId` is an FK. |
| `status`, `amount`, `currency` | `applied` or `duplicate`; positive amount in the payment currency's subunits; exact invoice currency. Unknown links or wrong money produce no row (`razorpayInvoicePaid`). |
| `amountInr`, `feeInr`, `taxInr`, `method`, `international` | Nullable payment API data: INR conversion, fee and GST on the fee in paise, method and international flag. `recordFees` reads it after the decision transaction; failed GET leaves stored data alone, absent amounts/method use `undefined`. `billing-fee-report.ts` refreshes missing fields. |
| `paidAt`, `createdAt` | Initially now on creation; successful `recordFees` overwrites paid time with Razorpay `created_at`. Failed GET leaves that time unchanged. DB creation time does not change (`recordPayment`, `recordFees`). |

SQL checks status and positive amount, indexes `(orgId, paidAt)` and `paidAt`, and cascades payment deletion with the invoice. It does not check currency, INR amounts, copied org/link ownership or whether an applied payment's invoice is paid. The migration also adds unique nullable link/payment IDs on `BillingInvoice` (migration above).

### Seller document input (not an app table)

`BillingDocument.seller` holds name, street lines, city, postal code (`zip`), state, country, GSTIN, email and `lutArn`. `documentOf` supplies Meteroid's default seller when drawing a new PDF; the app saves the PDF bytes, not a structured seller snapshot, on S3. `sellerCache` stores one successful result and fetch time in the module for 10 minutes. `BillingDocument.exemption` is `string[] | null`: exports have the declaration and a separate `LUT ARN: …` line; other exemptions have one reason (`web/lib/billing/documents.ts` `BillingDocument`, `billingDocument`; `web/lib/billing/meteroid.ts` `Seller`, `sellerDetails`; `web/lib/billing/billing.ts` `documentOf`, `keptPdf`).

## How it works

### Company details

1. The company's name, address, GSTIN, contact email and LUT ARN are read from Meteroid Settings › Invoicing entity, not app environment variables or a fixed PDF seller. `sellerDetails()` calls gRPC-web `InvoicingEntitiesService/GetInvoicingEntity` with no fields (the default entity). `meteroidGrpc` returns the first message frame's bytes, or an empty buffer if no first message frame exists. `decodeProto` groups values by field number; wire types 0, 1 and 5 become numbers, type 2 becomes bytes, and unsupported types throw (`web/lib/billing/meteroid.ts` `meteroidGrpc`, `decodeProto`, `sellerDetails`).
2. `defaultInvoicingEntity`, called by `sellerDetails`, decodes reply field 1 as the entity. It reads entity ID 1, legal name 4, legal footer 11, street lines 14/15, postal code 16, state 17, city 18, GSTIN 19, country 20 and email 41. `lutArnOf(footer)` takes the first non-space token after case-insensitive `ARN` with an optional `:`, `#` or `-`, or trims the whole footer when no such token matches. Bare ARNs and `LUT ARN: AD…` therefore work. Missing fields become empty strings. Missing entity, legal name or GSTIN throws; address/email and LUT ARN are not required or validated. A missing ARN still permits an export PDF with a placeholder (B24). A successful result is cached in the module for **10 minutes**. There is no refresh button, tenant-keyed cache or stale-cache fallback after expiry (`meteroid.ts` `Seller`, `defaultInvoicingEntity`, `lutArnOf`, `sellerDetails`, `SELLER_TTL_MS`).
3. Every newly drawn invoice/receipt document receives that seller. A saved PDF is read from S3 without fetching today's seller (`billing.ts` `keptPdf`). PDF seller text and author metadata use `doc.seller`; the PDF module's `SELLER` constant is gone. Only the service code `SAC = "998314"` remains fixed (`documents.ts` `SAC`, `BillingDocument`, `sheet`, `finish`, `renderInvoice`, `renderReceipt`; `billing.ts` `documentOf`).
4. Setup keeps a script-local seed for Forever Learning Solutions Pvt Ltd, its address, GSTIN 33AAGCF6592D1ZN and billing@trainertwin.com. It reads the default invoicing entity first (`defaultInvoicingEntity`); a failed read stops the script. When the entity has a GSTIN it is left alone (Meteroid edits are kept); otherwise that same entity (by its id) is seeded, including 2-day terms and the SAC footer (dry-run only logs the proposed write). Company edits and the year's LUT ARN belong in Meteroid afterwards. Setup seeds the SAC invoice footer (field 10), not the legal footer (field 11), and does not file or set an LUT ARN (`web/scripts/meteroid-billing-setup.ts` `SELLER`, `NET_TERMS`, entity step; `meteroid.ts` `defaultInvoicingEntity`, `sellerDetails`).

### Details and tax

1. `saveBillingDetails` parses before any billing change. Invalid data returns `BillingError` 400 with the first field path/problem. Unknown fields are rejected by `.strict()`. Strings are trimmed; country/tax ID uppercased; emails lowercased and deduplicated. Legal name/street are 1–200 characters, line2 at most 200, city 1–100, postal code 1–20, tax ID at most 50, email at most 320, 1–5 email entries before deduplication. Countries use `Intl.DisplayNames` with reserved/noncountry exclusions. Phone is required: remove spaces, hyphens, parentheses and dots, then require `+`, a nonzero first digit and 8–15 digits total (`web/lib/billing/details.ts:61–88` `billingDetailsInput`, `countryName`).
2. India requires a listed GST state code (retired 25/28 absent). An optional GSTIN must match the 15-character pattern, pass its mod-36 checksum and match the state's first two digits. A non-India state is refused (`billingDetailsInput`, `gstinChecksumOk`).
3. `locked` serializes details and pack requests with a PostgreSQL org advisory transaction lock, timeout 60 seconds / max wait 30 seconds. The Meteroid customer PATCH runs **before** the local update. External failure rolls back the app update; there is no shared transaction with Meteroid (`billing.ts` `locked`, `saveBillingDetails`, `viaMeteroid`).
4. `meteroidCustomerPatch` sends name, address, tax ID, phone, first billing email plus all invoicing emails, custom taxes and export exemption. India prints `State name (code)` on line2, appended to the entered line2, and also sends the state field. Tamil Nadu (33) gets CGST 9% + SGST 9%; other India IGST 18%; outside India no tax and `exemption_reason = EXPORT_DECLARATION`, exactly “Export of services without payment of tax under LUT”. The customer patch contains no ARN. A new app PDF adds the ARN from the seller's legal footer (`details.ts` `addressLine2`, `taxFor`, `EXPORT_DECLARATION`, `meteroidCustomerPatch`; `documents.ts` `billingDocument`; `meteroid.ts` `lutArnOf`). Meteroid applies the customer's tax when issuing invoices; invoice copies keep Meteroid's amounts (`billing.ts` `recordInvoice`).

### Upgrade and cancellation

1. Staff create the org's subscription in Meteroid on its own `CUSTOM` plan, with tax-inclusive USD pricing, its own payment terms and no automatic collection ([Billing](billing.md) rules 2, 6, 10). The app has no `requestUpgrade`, `billing.upgrade`, `createPaidSubscription` or `paidPlan`; it does not look up a shared `Paid` plan or choose a price. Trial's Billing page says to contact TrainerTwin, and has no Upgrade button (`web/lib/billing/trpc.ts` `billingRouter`; `web/components/billing/billing-page.tsx` `PlanSection`; `web/lib/billing/meteroid.ts` exports).
2. Meteroid's first positive finalized invoice reaches `syncInvoice` through the webhook, or `syncOrgInvoices` through the daily check. While Trial has no stored paid ID, `kindOf` reads the invoice's subscription: any plan name other than exactly `TRIAL_PLAN = "Credits"`, with status ACTIVE / PENDING_ACTIVATION / PENDING_CHARGE, qualifies. It saves that ID only if the DB paid ID is null, then reads it back: only the subscription that became the org's paid ID makes its invoice the `upgrade`; a second one at the same time is `other`. The app stays Trial until paid. No billing-details, `CUSTOM` type, price, currency or exclusive-plan-ownership check runs during adoption; staff setup is the boundary (`billing.ts` `kindOf`, `recordInvoice`, `syncInvoice`; `meteroid.ts` `getSubscription`, `TRIAL_PLAN`).
3. The issued workflow tries to create the invoice's Razorpay link and emails it. Overview exposes the pending copy and its saved Pay now URL; no upgrade request returns a subscription or payment URL anymore. Meteroid owns renewal dates and terms on the staff-created subscription, not an app constant (`web/workflows/invoice-issued.ts` `invoiceIssued`; `billing.ts` `billingOverview`; `billing-page.tsx` `PlanSection`). Choosing and switching plan options is future work, issue #19 ([Billing](billing.md) rule 2).
4. `invoicePaid` refreshes payment first. It activates Paid when the stored subscription matches, or when the stored ID is null and Meteroid says the invoice's subscription is ACTIVE / PENDING_ACTIVATION / PENDING_CHARGE. A different stored ID, or a cancelled subscription with no stored ID, leaves the plan unchanged, logs for staff and emails “We'll be in touch about your plan.” Matching IDs bypass the live-status check (B14 below). No plan credits are granted.
5. At overdue time, `invoiceOverdue` refreshes Meteroid first. Set `overdueAt` before voiding an unpaid upgrade by gRPC, then set the copy void and cancel its subscription effective today by REST. A failed void re-reads payment: PAID means no cancellation. Cancellation errors are tolerated only if the subscription is already CANCELLED / COMPLETED / ABORTED. Clear the matching Trial subscription ID and send upgrade-cancelled email. A void upgrade with `overdueAt` continues from cancellation on retry; failed cancellation/email is also retried by the daily check. Other void invoices stop.
6. Signed cancelled/ended events resolve by subscription ID **before** any customer/org lookup, clear the matching Paid subscription ID, set Trial and clear pause. The daily check also reads a stored subscription's status and applies this effect for CANCELLED / COMPLETED / ABORTED. There is no customer cancel button (`paidSubscriptionEnded`, `syncOrgInvoices`; webhook POST; `billing-page.tsx` `PlanSection`).

### Buy packs

`buyPacks` accepts whole packs 1–10. Details must exist (400); the plan must be Paid and not paused (409, with separate messages). `packPrice` calculates the net cents near `floor(gross × 10000 / (10000 + total tax bp))`: try ±5 net cents, round each tax half upward separately, choose the closest total not above $25 × packs, at most one cent short. Divide net dollars by credits and give Meteroid an 8-decimal unit price; assert that it rounds back to net cents (`web/lib/billing/pricing.ts` `packPrice`, `totalWithTax`).

POST the Meteroid top-up with `amount = packs × 100`, `MINS`, `collection: SEND_INVOICE`, the net unit price and expiry at 23:59:59 UTC on request day +365 days. Key: `pack-<org>-<requestId>`. Read/store the invoice afterward and request its payment link through `payLinkQuietly`; return `{invoiceId, number, totalCents, payUrl}`. Read failure is logged and returns its ID with null number/total/URL. Link failure gives null URL without undoing the pack invoice. A non-null URL redirects this tab to Razorpay (`billing.ts` `buyPacks`, `packExpiry`; `meteroid.ts` `createPackInvoice`; `billing-page.tsx` `BuyPacksDialog`). The tRPC input requires a UUID. `BuyPacksDialog` keeps one UUID for the selected quantity: an error retry reuses it, a quantity change or successful response generates a new one. It is component state, not persisted across reloads (`billing-page.tsx` `BuyPacksDialog`).

The pack-creation function does not grant credits or mark paid. A validated Razorpay payment marks the invoice paid through the shared handler below; payments made outside Razorpay are still marked by staff in Meteroid. Meteroid grants PAID credits after payment; `wallet.funded` schedules `syncOrgCredits`, which refreshes the balance/grants and announces new grants to the admin. The paid invoice email and that credit-added email are separate. See [Credits](credits.md#how-it-works) (`web/app/api/meteroid/webhook/route.ts` POST; `web/lib/schedule-org-credits.ts` `scheduleOrgSync`; `web/workflows/sync-org-credits.ts` `syncOrgCredits`).

### Copy invoices and claim workflows

`syncInvoice` GETs the invoice, resolves its customer to an org unless an org was supplied, then calls `recordInvoice` and `startInvoiceWorkflows`. A first-seen nonpositive, DRAFT or VOID invoice is ignored. `UNCOLLECTIBLE` maps to void; PAID maps to paid; partial/processing/errored payment maps to unpaid. A paid/void copy cannot regress to unpaid, but paid and void can replace each other. Existing copies update amounts/dates/references, not kind/org (`billing.ts` `recordInvoice`, `statusOf`).

For early upgrade webhooks, `kindOf` can recognize any non-`Credits` subscription while Trial has no stored ID and set that ID, but only when Meteroid reports ACTIVE / PENDING_ACTIVATION / PENDING_CHARGE. Otherwise matching current subscription + Trial means upgrade, matching + Paid means renewal, nonmatching subscription means other. The adoption branch reads the stored paid ID back after its conditional update, so only the winner is the upgrade. No-subscription packs use the exact Meteroid line name `Purchase credits` (`billing.ts` `kindOf`; `meteroid.ts` `toInvoice`).

Atomic claims precede workflow startup. Non-void invoices claim issued once; paid invoices claim paid once. The `invoice.paid` webhook passes a paid hint even when the API still returns unpaid, so the paid workflow starts then too. Startup failure logs and clears the claim; a started-but-dead workflow retains its claim for daily repair (`billing.ts` `claim`, `startInvoiceWorkflows`).

### Invoice timers, payment, pause and resume

- `invoiceIssued` refreshes, returns immediately if void, tries the `payLink` step when unpaid, then sends the issued email. A link-step failure is caught so the invoice email can still go out, asking the customer to reply for a payment link; daily repair retries missing links (`web/workflows/invoice-issued.ts:17–24`; `web/workflows/steps/billing.ts:18–22` `payLink`). Pack/other stop there. Renewal sleeps to 00:00 UTC the day before due and calls `invoiceReminder`, then sleeps to overdue time. Upgrade only sleeps to overdue time. Past times cause no sleep. Reminder refreshes, requires renewal/unpaid and the exact UTC day before due. Overdue handling refreshes and requires overdue plus unpaid, or a void upgrade with an existing overdue marker (`web/workflows/invoice-issued.ts` `invoiceIssued`, `until`; `web/lib/billing/billing.ts` `invoiceReminder`, `invoiceOverdue`).
- Overdue renewal writes `overdueAt` and pauses only a matching current subscription on Paid. Re-read Meteroid **after** the pause; if paid meanwhile, call `invoicePaid` to undo the pause and process payment instead of sending paused mail. Otherwise send the pause email only if the org is still paused on that subscription. No invoice kind other than renewal pauses (`billing.ts` `pauseFor`, `invoiceOverdue`).
- `invoicePaid` workflow makes **12 checks**, each calling `handlePaid` (which refreshes Meteroid), with a 10-second sleep after each unpaid check. PAID stops the loop. If all checks remain unpaid it returns `not_paid`; later daily checks can repair it. This covers Meteroid sending invoice.paid before its GET API shows PAID (`web/workflows/invoice-paid.ts` `invoicePaid`; `web/workflows/steps/billing.ts` `handlePaid`).
- The library `invoicePaid` applies the effect **before** sending email: upgrade activates Paid under the subscription guard above; renewal counts only the org's **current subscription's** other unpaid overdue renewal copies and clears pause if none remain. Old renewals neither block current unpause nor allow unpause while a current renewal is overdue. Renewal email outcome comes from `pausedAt` after the update: active, or still paused until the other overdue invoice is paid. Pack reports credits being added by Meteroid; other has no plan effect. Repetition re-applies these effects and checks the email marker (`billing.ts` `invoicePaid`).
- New voice calls read only `pausedAt` and return `MinutesError` 403 before closing other learner calls or reading call balances. Studio: “Your organization's plan is paused because an invoice is overdue. Pay it on the Billing page to continue.” Learner: “Practice is paused for this organization right now. Please ask your trainer.” Live resume returns before this check; pause does not change existing allowances or remove credits. Staff chat is unaffected (`web/lib/billing/paused.ts` `pausedReason`; `web/lib/interview-sessions.ts` `activateSession`; [Sessions](sessions.md)).
- Learner grants call `refuseWhenPaused` before writing. Starting grants only check if somebody actually needs a first grant; no-op/fully skipped batches can succeed. People additions run starting grants before account/member creation, so ordinary new learners are refused while team/admin additions do not use this check (`web/lib/minutes.ts` `grantMinutes`, `giveStartingMinutes`, `grantMinutesToMany`, `refuseWhenPaused`; `web/lib/org-people.ts` `addPeopleToOrg`; [Credits](credits.md)).

### Emails and PDFs

`emailOnce` reads the invoice's event marker. Billing recipients are the current details' emails or the enabled admin; no recipient logs and returns false. Issued/reminder/paused/paid obtain the app's invoice PDF; paid also obtains its receipt. `keptPdf` reads a saved S3 object when the row has its key and S3 is configured, without Meteroid JSON, seller lookup or rendering. With configured S3 and a null caller key, it takes a PostgreSQL transaction advisory lock `pdf:<field>:<invoice id>`, rereads the stored key and reuses the winner's object if present. Only if still null does it draw, upload and save the key in that transaction. Timeout/max wait are both 60 seconds. Without S3 it draws on every call. Paid mail can therefore make zero, one or two document JSON reads, depending on which PDFs are already kept. There is no PDF-readiness polling or Meteroid PDF download. JSON/seller/render/S3 upload/read/DB-key failures throw before sending and leave the event marker null for retry. Send via Resend with `billing-<event>-<invoice id>`, then save the marker. Ordinary send failure throws. Missing `RESEND_API_KEY` is treated as completion even though sending was skipped (`billing.ts` `recipients`, `documentOf`, `keptPdf`, `invoicePdf`, `receiptPdf`, `emailOnce`; `web/lib/s3.ts` `getObjectBytes`, `putObject`, `s3Configured`; `web/lib/email.ts` `sendBillingEmail`, `sendEmail`).

Keys are `<orgPrefix>/billing/<number>-<invoice id>.pdf` and `<orgPrefix>/billing/RCPT-<number>-<invoice id>.pdf`. A download can create the first kept copy before any email; drawing/uploading happens before sending, so even a failed send can leave a kept PDF. A saved-key read failure does not redraw or repair the object. Concurrent/stale-null-key callers wait on the per-document lock and reread the winner's key, avoiding repeat draws/PUTs. S3 upload and DB commit are still separate: a successful upload followed by rollback can leave an unreferenced object, but no PDF is returned by that failed call. These keys have no billing-specific expiry or cleanup in this module (`billing.ts` `keptPdf`; `web/lib/s3.ts` `orgPrefix`, `getObjectBytes`, `putObject`).

| Event | Attachment / saved field |
| --- | --- |
| issued (all non-void kinds) | `<number>.pdf` / `issuedEmailAt` |
| reminder (unpaid renewal, due-tomorrow day only) | `<number>.pdf` / `reminderAt` |
| paused (current renewal) | `<number>.pdf` / `overdueEmailAt` |
| upgrade_cancelled | None / `overdueEmailAt` |
| paid (all paid kinds) | `RCPT-<number>.pdf`, then `<number>.pdf` / `paidEmailAt` |

`emailOnce` supplies `payUrl = paymentLinkUrl` only for a locally unpaid row. Issued/reminder/paused HTML adds a “Pay <amount> now” button; plain text adds “Pay online: <URL>”. Without a URL, both say “To pay invoice <number>, reply to this email and we'll send you a payment link.” Paid/cancelled templates have neither payment button nor this fallback. There are no bank details or payment-instructions input (`billing.ts` `emailOnce`; `web/lib/email.ts` `BillingEmailArgs`, `billingEmail`). Customers pay on Razorpay's hosted page: card, or bank transfer where Razorpay offers it. Bank transfers, if wanted (for example International bank transfers / MoneySaver), are enabled in Razorpay itself, not implemented or configured by TrainerTwin ([Billing](billing.md) rule 20; `web/components/billing/billing-page.tsx` `InvoicesSection`; `web/lib/razorpay.ts` `createInvoicePaymentLink`). `billingEmail` also builds escaped HTML and plain text, with Billing URL, amounts formatted in the invoice's currency by `pricing.ts` `formatMoney`, due date and payment outcome on paid. Default sender is `TrainerTwin Billing <billing@trainertwin.com>`, configurable by `BILLING_FROM_EMAIL`, reply-to support@trainertwin.com; the Meteroid seller email does not set the email sender or reply-to. Full subjects/recipient boundaries: [People and emails](invites-and-emails.md#billing-emails) (`web/lib/email.ts` `billingEmail`, `sendBillingEmail`, `sendEmail`).

When a PDF needs drawing, `documentOf(row)` first reads local `BillingPayment` IDs/methods for this invoice. It then reads `getInvoiceRaw(row.id)`, the org's name and `sellerDetails()` in parallel, and calls `billingDocument(raw, orgName, seller, methods)` with the payment-ID-to-method map. The seller is today's default entity (up to 10 minutes cached), not an invoice-time seller snapshot. Both PDFs use `customer_details`, Meteroid's **invoice-time customer snapshot**, not today's app details or a fresh customer lookup. The snapshot supplies buyer name, address, email and tax ID; only a missing/empty customer name falls back to the current org name. India uses GSTIN and state/code for place of supply; the state suffix on address line2 is moved after city/postal code. Outside India uses Tax ID and “Outside India (export of services)” (`billing.ts` `documentOf`; `meteroid.ts` `RawInvoice`, `getInvoiceRaw`; `documents.ts` `billingDocument`).

`billingDocument` maps invoice number, issue/due dates, currency, subtotal, total, tax breakdown and every line. Line amounts are rounded from quantity × unit price; unit prices allow four decimals. `Purchase credits` becomes minute-pack wording, every line gets SAC 998314, and a period's exclusive end becomes its last covered day. Positive non-exempt taxes print their name/rate. When the invoice-time customer has a non-India country, `exemption` is two strings: `EXPORT_DECLARATION` and `LUT ARN: <seller.lutArn>`, regardless of the old invoice exemption reason. Missing ARN prints “LUT ARN: (to be added in Meteroid › Invoicing entity › legal footer)”, not a refusal. India or missing-country snapshots use the first tax exemption reason (default “Exempt from GST”) as a one-string array, or null when no exemption exists. `linesAndTotals` wraps and prints each string separately. Payment history includes only SETTLED non-refund transactions: reference, processed date and cents. A reference in the local method map prints Card, UPI, Netbanking, Wallet, EMI or Bank transfer with “(Razorpay)”; unknown/null Razorpay methods print “Online (Razorpay)”. References absent from the map print “Bank transfer”, including other outside-Razorpay methods (`documents.ts` `billingDocument`, `METHOD`, `describe`, `period`, `money`; `billing.ts` `documentOf`).

Both renderers take a `BillingDocument`, not billing details or a `BillingInvoice`. They draw one A4 page with title/numbers top left, TrainerTwin mark top right, seller/buyer side by side, amount, line table and totals. Seller name, street lines, city/postal code, country name, GSTIN and contact email come from `doc.seller`; empty address/email lines are omitted. The separate seller `state` field is read but not printed, so a state must be included in the street lines to appear. Every invoice line uses the fixed `SAC` 998314. The **app's invoice PDF is the tax invoice** (`documents.ts` `SAC`, `sheet`, `linesAndTotals`, `finish`; `meteroid.ts` `sellerDetails`).

- On first drawing, `invoicePdf(row)` calls `renderInvoice(doc, row.status === "unpaid" ? row.paymentLinkUrl : null, row.status === "unpaid")` through `keptPdf`: an unpaid copy with a URL prints “Pay online” and the URL with a clickable PDF link; an unpaid copy without one says to write to the seller's email for a payment link, quoting the invoice number. No bank details. Other content: invoice number, UTC issue/due dates, place of supply, amount due, lines, taxable value/tax/total/amount due, exemption wording and computer-generated/no-signature footer. With S3 and the saved key, later paid mail/downloads reuse that first copy, including its original Pay online link or no-link guidance and full amount due. Payment does not redraw a kept tax invoice (`billing.ts` `invoicePdf`, `keptPdf`; `documents.ts` `renderInvoice`, `Sheet.link`).
- On first drawing, `receiptPdf(row)` calls `renderReceipt(doc, row.paidAt ?? row.updatedAt)` through `keptPdf`: invoice number, `receiptNumber(number)` = `RCPT-<number>`, UTC date paid, place of supply, full amount paid, the same lines/totals and a payment-history table with method/reference/date/amount/receipt number. Without settled transactions, one bank-transfer row uses the full invoice total and that paid date. Its footer points to the invoice as the tax invoice (`billing.ts` `receiptPdf`; `documents.ts` `receiptNumber`, `renderReceipt`).

Amounts use the invoice currency. Fixed Helvetica fonts use WinAnsi: unsupported currency symbols (such as ₹) use a currency code instead (`money`), other unsupported characters become `?` (`safe`). Descriptions and exemption wording wrap at words; seller/buyer fields, payment links and payment-history rows do not. Identical document/render inputs yield identical bytes: automatic metadata updates are off; creation/modification dates use the invoice issue day or receipt paid timestamp, never the render clock. With S3, later calls carrying the saved key reuse the bytes rather than reread render inputs; without S3, current inputs can change the same invoice's bytes. S3 reuse and the locked first draw resolve B15's byte-drift issue and B25's concurrent/stale-key overwrite (`billing.ts` `keptPdf`; `documents.ts` `money`, `safe`, `Sheet.wrap`, `finish`, both renderers).

`orgInvoice` scopes downloads to the signed-in org (404 otherwise). A saved-key PDF with S3 configured needs only the local row and S3 object, so it can download while Meteroid is down. An unkept PDF (or any PDF without S3 configured) needs live Meteroid JSON and a successful seller read or unexpired cache. `viaMeteroid` maps failures to 502, including S3 errors under the same billing-system message; it does not distinguish storage failures from Meteroid failures. Attachment failures leave the email marker unset; upgrade-cancelled mail needs no PDF or seller. Receipt requires stored paid status (409 otherwise), checked before obtaining the PDF. There is no 409 “PDF not ready”. Routes require authentication (401), enabled studio membership (403 otherwise), PDF content type, attachment filename, private/no-store (`billing.ts` `invoicePdfFor`, `receiptPdfFor`, `viaMeteroid`; both invoice GET routes). UI download buttons use `fetch`, read the blob, click a temporary object-URL download and revoke it. The tab's `OrgPin` fetch wrapper sends its org header, unlike a plain anchor; non-OK responses toast the route error (`billing-page.tsx` `download`; `web/components/org-pin.tsx` `install`).

### Daily repairs and local UI

`checkAllBilling` visits every `OrgBilling`, isolates per-org errors and returns results. `syncOrgInvoices` does this (`billing.ts` `syncOrgInvoices`, `checkAllBilling`; `meteroid.ts` `listInvoices`):

1. Read the newest **50** Meteroid invoices, record them and start missing workflows. A claim is considered dead after **10 minutes** without its email (wall-clock `Date.now`, not the supplied simulated `now`). Directly handle missing paid effect/email first; otherwise missing issued email. These repair failures log and continue; record/start errors can still abort this org's pass.
2. Read **all local unpaid copies**, not only the recent 50. If a link ID exists, ask Razorpay and settle a paid link through `reconcilePaymentLink`; otherwise call `ensurePaymentLink`. This loop is unconditional. Missing Razorpay keys fail each API attempt, log and leave the invoice for a later pass. The first Meteroid list still has to succeed before this loop can run (`web/lib/billing/billing.ts` `syncOrgInvoices`; `web/lib/razorpay.ts` `env`, `call`).
3. Select local overdue upgrade/renewal copies with `overdueEmailAt = null`: unpaid rows, plus void upgrades whose `overdueAt` is non-null. Call `invoiceOverdue` for each in its own try/catch. This finishes partial upgrade cancellation and repairs missing paused mail even after `overdueAt` was written. One overdue failure does not stop later rows.
4. If paused, count unpaid overdue renewals of the **current subscription**. Clear pause if none remain (including when the overdue invoice was voided).
5. GET the stored Paid subscription, including a pending Trial subscription. CANCELLED / COMPLETED / ABORTED calls `paidSubscriptionEnded`: Trial, no ID, unpaused. This status-read failure can abort the org's result after earlier repairs.

No direct reminder repair runs. A newly restarted issued workflow still calls `invoiceReminder`, which sends only on the correct day; missed reminders are best effort, never sent later.

Vercel GET cron `/api/internal/billing/check` runs **daily at 00:15 UTC** (`web/vercel.json`). Route GET/POST accepts Bearer or x-internal-secret matching `CRON_SECRET`, falling back to `INTERNAL_API_SECRET`. No configured secret allows only off-Vercel execution; on Vercel it fails closed. Route limit is 300 seconds; per-org errors still return `{ok:true, orgs}` (`web/app/api/internal/billing/check/route.ts` `isAuthorized`, GET).

`billingOverview` reads only the app, newest 100 invoice copies, and supplies plan/details/pack prices, pending upgrade and latest matching unpaid/overdue renewal views. `planCents` is the total of the newest non-void `upgrade` or `renewal` copy matching the stored paid subscription, or null. It is the last invoiced amount, not a live plan rate or an app price override. `PlanSection` formats that amount as USD “a month, tax included”; absent price shows “Your paid plan”. No shared $300 fallback remains (`billing.ts` `billingOverview`; `billing-page.tsx` `PlanSection`). Each locally unpaid view carries `payUrl`, including overdue views; paid/void carry null (`billing.ts` `billingOverview`). `InvoicesSection` adds Pay now to unpaid/overdue rows with a URL; `PlanSection` adds it to pending-upgrade and paused-renewal notices. These use `window.location.assign`, not an embedded checkout. Pending-upgrade and paused notices without a URL say to add a phone number to billing details to pay online, or reply to the invoice email; `InvoicesSection` says card or bank transfer where offered, never bank details on the invoice (`billing-page.tsx` `PayNow`, `PlanSection`, `InvoicesSection`). Return-page confirmation and polling are described below. On Paid, `renewsOn` is the largest `periodEnd` among non-void copies matching the current subscription, or null without a period. This is an invoice-derived date, not a live subscription lookup. The Billing page shows it beside the monthly price; details; packs only on Paid, with expiry copy “a year after the invoice date”; invoice statuses/download buttons and paid receipts. Paused pack purchase is disabled. `/settings?tab=billing` redirects to `/billing`. `BillingBanner` fetches its own overview key, stale time 5 minutes, retries off: pause alert first, otherwise **any current-subscription** unpaid renewal's due date (not only tomorrow). It has no polling interval (`web/lib/billing/billing.ts` `billingOverview`; `web/components/billing/billing-page.tsx` `BillingPage`, cards; `billing-banner.tsx` `BillingBanner`; `web/app/dash/billing/page.tsx`; `web/app/dash/layout.tsx` `DashLayout`).

### Razorpay: collecting invoice payments

#### Make and show a link

1. Razorpay is always on ([Billing](billing.md) rule 27). `ensurePaymentLink` reads the invoice and current billing details. A saved URL is returned first; without one, only an unpaid positive invoice with a phone qualifies. Missing phone logs and returns null. Missing `RAZORPAY_KEY_ID` or `RAZORPAY_KEY_SECRET` throws when creating a link; it is not an off-mode no-op. Request handlers catch this and return null `payUrl`; the issued workflow catches it and emails without Pay now, asking for a reply to get a link; the daily check retries. Saving a phone or configuring keys does not itself make links: a request/workflow/daily check must run afterward (`web/lib/billing/razorpay.ts` `ensurePaymentLink`; `web/lib/razorpay.ts` `env`, `call`; `web/lib/billing/billing.ts` `payLinkQuietly`, `syncOrgInvoices`; `web/workflows/invoice-issued.ts` `invoiceIssued`).
2. Create for exact `totalCents`/`currency`, description `TrainerTwin invoice <number>`, unique Razorpay reference = invoice ID, notes `invoiceId`/`invoiceNumber`/`orgId`, and today's legal name, first email and phone. Disable partial payment, email, SMS and reminders; omit expiry; use GET callback `<studioUrl>billing?paid=<encoded number>`. Currency follows the invoice, not a USD override (`web/lib/billing/razorpay.ts` `callbackUrl`, `ensurePaymentLink`; `web/lib/razorpay.ts` `createInvoicePaymentLink`).
3. Razorpay HTTP 400 on create triggers a reference lookup and reuses the existing link if found; other errors propagate. An ID-null conditional update saves ID/URL and rereads the winner's URL. Creation relies on Razorpay's unique reference, not an app lock (`web/lib/billing/razorpay.ts` `ensurePaymentLink`; `web/lib/razorpay.ts` `paymentLinkByReference`).
4. Issued workflow tries the link before email; only the pack handler returns `payUrl`. Overview/mail expose saved URLs while locally unpaid; a newly drawn invoice PDF follows the same rule, but a kept PDF preserves its first link or no-link guidance even after payment or late link creation. Buttons redirect to the hosted page, never collect card details in TrainerTwin. Link failure does not undo an invoice or hold up invoice mail asking the customer to reply for a link. Late-link email/PDF coverage is B20 (`web/workflows/invoice-issued.ts` `invoiceIssued`; `billing.ts` `buyPacks`, `billingOverview`, `emailOnce`, `invoicePdf`, `keptPdf`; `billing-page.tsx` `PayNow`, `BuyPacksDialog`).

#### Webhook and settlement

POST `/api/razorpay/webhook` always reads the body and checks its signature; there is no off-mode 404. Missing signature returns 401 before looking up the secret. With a supplied signature, missing `RAZORPAY_WEBHOOK_SECRET` throws; a bad HMAC with a configured secret returns 401. Signed `payment_link.paid` with truthy `notes.invoiceId` and a payment entity goes to `razorpayInvoicePaid`; lookup uses the saved **link ID**, not the note's invoice ID. Other paid links and `invoice.paid` retain phase 1 purchases. `refund.processed` uses only phase 1's log-only refund helper; phase 3 refunds/credit notes are manual (`web/app/api/razorpay/webhook/route.ts` POST; `web/lib/razorpay.ts` `verifyWebhookSignature`, `env`; [Payments](payments.md#webhooks-and-refunds)).

`razorpayInvoicePaid` does this (`web/lib/billing/razorpay.ts` `razorpayInvoicePaid`):

1. Unknown link or amount/currency unequal to the invoice logs and returns `ignored` before changing data. The webhook returns 200 `{ok:true,result}` for ignored/applied/duplicate outcomes. Other unexpected errors escape for retry; phase 1 `PurchaseError` is acknowledged 200. Signed JSON/entities are cast, not runtime-validated, so malformed signed bodies can throw (`web/lib/billing/razorpay.ts` `razorpayInvoicePaid`; `web/app/api/razorpay/webhook/route.ts` POST).
2. Take a per-invoice PostgreSQL advisory transaction lock (`razorpay:<invoice id>`, timeout 60 seconds / max wait 30 seconds). Reread: same accepted `razorpayPaymentId` means applied retry; another saved ID means duplicate. Neither asks Meteroid to mark again (`web/lib/billing/razorpay.ts` `razorpayInvoicePaid`).
3. With no accepted ID, read Meteroid JSON. A transaction with this payment reference recovers a successful remote mark whose local save was lost. Otherwise PAID or VOID means duplicate. For an unpaid invoice, write accepted ID and call `markInvoicePaid(id, (amount / 100).toFixed(2), paymentId)` within the local transaction. The ID commits only when the mark call and DB commit succeed. This stops concurrent webhook/confirm/daily calls from marking twice while Meteroid still reads UNPAID, but does not make the remote mark atomic with PostgreSQL (B16) (`web/lib/billing/razorpay.ts` `razorpayInvoicePaid`; `web/lib/billing/meteroid.ts` `markInvoicePaid`).
4. `recordPayment` upserts `BillingPayment` as applied/duplicate **inside** the decision transaction, including accepted-ID retries and reference recovery. A new accepted ID and payment row are written before the remote mark. **After** commit, `recordFees` GETs the Razorpay payment best-effort; API failure leaves existing data alone, successful reads update available fee/method data and paid time. Duplicate logs its reason and refund instruction, then stops. Applied calls `syncInvoice` with a paid hint to claim the existing invoice-paid workflow despite a stale unpaid GET. That workflow polls Meteroid, activates Paid/unpauses and sends receipts; Meteroid grants pack credits (`razorpay.ts` `recordPayment`, `recordFees`, `razorpayInvoicePaid`; `billing.ts` `syncInvoice`, `startInvoiceWorkflows`, `invoicePaid`; `web/workflows/invoice-paid.ts` `invoicePaid`).

`closePaymentLink` is called on handled bank payments, explicit invoice voids and overdue-upgrade cancellation. It skips only no-link/accepted-Razorpay-ID rows, tries cancel, logs **all** errors (including missing API keys) and returns success to its caller. IDs/URLs stay stored. No durable cancellation marker/retry queue exists (B18) (`web/lib/billing/razorpay.ts` `closePaymentLink`; `web/lib/billing/billing.ts` `invoicePaid`, `invoiceVoided`, `invoiceOverdue`).

#### Return page and missed webhook

- `PaymentArriving` reads `paid` and `razorpay_payment_link_id`. It calls `billing.confirmPayment` once for a link ID and invalidates overview afterward. When the named invoice is not locally paid, it polls overview every **3 seconds for up to 2 minutes**, then shows taking-longer copy. Invoice-number matching is only UI state, not proof of payment (`web/components/billing/billing-page.tsx `PaymentArriving``).
- Studio-only `confirmPayment` accepts `plink_` plus alphanumeric characters and finds the link in the active org (404 otherwise). Paid/void returns local status. Unpaid asks Razorpay through `reconcilePaymentLink`, returning applied/duplicate/ignored or pending. Provider/DB failure logs and returns pending for webhook/daily repair (`web/lib/billing/trpc.ts:41–55`).
- `reconcilePaymentLink` returns null only before the request when no link ID exists; otherwise it GETs the link and requires status `paid`. Missing API keys throw rather than returning an off-mode no-op. It chooses the first captured payment, falling back to the first listed payment, then hands its ID/amount and link currency to the **same** `razorpayInvoicePaid` handler. Daily sync repairs every local unpaid copy or makes its missing link. It does not enumerate all payments on already-paid invoices (`web/lib/billing/razorpay.ts` `reconcilePaymentLink`; `web/lib/billing/billing.ts` `syncOrgInvoices`).

#### Fee report

From `web/`, `bun scripts/billing-fee-report.ts --month YYYY-MM > fees.csv` selects local `BillingPayment.paidAt` within the UTC month, oldest first, including duplicates. It refreshes and saves API data for payments missing fee, INR conversion, tax on fee or method. Settlement reconciliation reads batches of 1000 for the requested month **and next month**, joining settlement ID/date to payment entries. Failures silently leave blanks. CSV contains paid timestamp, payment ID, status, invoice, org slug, amount/currency, INR conversion, fee, GST on fee, calculated net, method, international flag, settlement ID/date. Monetary subunits divide by 100; net = `amountInr - feeInr` (code treats fee as including GST). Settlement metadata is joined at report time, not stored locally. CSV cells quote commas/quotes/newlines; stderr prints payment/duplicate counts. Month syntax requires YYYY-MM and range 01–12. Missing-field/settlement limits are B19 (`web/scripts/billing-fee-report.ts:12–64`; `web/lib/razorpay.ts` `settlementRecon`).

### Lifecycles in words

- Plan: Trial → staff subscribe in Meteroid → first invoice adopted → Trial with pending paid subscription → upgrade payment → Paid → overdue current renewal → Paid paused → all current-subscription overdue renewals paid/void → Paid unpaused. Pending upgrade overdue → void + cancel → Trial without pending ID. Cancelled/ended current paid subscription → Trial unpaused (`billing.ts` `kindOf`, `invoiceOverdue`, `invoicePaid`, `paidSubscriptionEnded`).
- PDF: null caller key → per-document lock → reread key → read the winner's S3 object, or draw → upload → save key → commit. Later key-bearing calls read S3 directly. Without S3, every call draws anew. Email completion is separate from PDF retention (`billing.ts` `keptPdf`, `emailOnce`).
- Invoice: unseen finalized positive invoice → unpaid copy → paid or void. Paid/void never → unpaid by a stale read. Pack/other can remain unpaid indefinitely without pause (`recordInvoice`, `invoiceOverdue`).
- Delivery: null claim → claimed timestamp → workflow started → email marker; startup failure → null claim; claimed >10 minutes without email → direct daily repair. Send failure leaves marker null; successful send (or missing Resend key) sets it (`claim`, `startInvoiceWorkflows`, `emailOnce`, `syncOrgInvoices`).

## Rules

1. All four billing tRPC procedures, including `confirmPayment`, require admin/team; learners are FORBIDDEN. PDF access is same-org studio only (`web/lib/billing/trpc.ts` `billingRouter`; `web/lib/trpc.ts` `studioProcedure`; PDF GET routes).
2. Invalid details return the first problem with 400 before any remote write; valid saves patch Meteroid before app JSON (`billing.ts` `saveBillingDetails`; `details.ts` `billingDetailsInput`). Unknown detail fields are rejected by `.strict()`.
3. There is no self-serve upgrade procedure or button. Adoption checks a Trial/null-paid-ID snapshot and a live non-`Credits` subscription, then conditionally stores its ID. Only the subscription that actually became the org's paid ID is its upgrade (it reads the ID back); a second one at the same time is `other`. (`billing.ts` `kindOf`; `meteroid.ts` `TRIAL_PLAN`; `trpc.ts` `billingRouter`; `billing-page.tsx` `PlanSection`).
4. Whole packs 1–10 require details, Paid and no pause. Pack total cannot exceed nominal price and is at most one cent short for supported taxes (`billing.ts` `buyPacks`; `pricing.ts` `packPrice`).
5. Razorpay invoice payment handling calls Meteroid `markInvoicePaid`; app pack creation and staff subscription adoption do not. Meteroid, not this app, grants the paid top-up credits (`web/lib/billing/razorpay.ts` `razorpayInvoicePaid`; `meteroid.ts` `markInvoicePaid`, `createPackInvoice`; `billing.ts` `invoicePaid`).
6. First-seen zero/draft/void invoices are ignored; DB rejects totals ≤0. Known kinds persist; stale reads cannot make paid/void unpaid (`billing.ts` `recordInvoice`; billing migration).
7. At most one issued and paid workflow claim wins concurrently per invoice. A failed start releases it (`billing.ts` `claim`, `startInvoiceWorkflows`).
8. Only unpaid renewals get reminders on the UTC day before due; only current Paid renewal copies can pause. Upgrade overdue voids/cancels, pack/other never pause (`invoiceReminder`, `invoiceOverdue`, `pauseFor`).
9. Call/grant refusal reads only local pause state; resumes bypass pause. No billing pause operation removes credit cache or ledger balances (`paused.ts` `pausedReason`; `interview-sessions.ts` `activateSession`; `minutes.ts` `refuseWhenPaused`; `billing.ts` `pauseFor`).
10. Paid renewal processing clears pause only when no other overdue unpaid renewal copy of the current subscription exists, and the email outcome reflects pause state after the update. Paid plan/effects happen before receipt email (`billing.ts` `invoicePaid`).
11. Billing event email uses its stored marker and Resend event key. Failed sends retain null markers, except missing Resend configuration. Paid emails attach receipt then invoice (`billing.ts` `emailOnce`; `web/lib/email.ts` `sendEmail`).
12. Signed Meteroid callbacks accept flat or `data` fields, with flat fields winning. Bad signature is 401; malformed JSON 400; unknown customers/types are acknowledged and ignored, except subscription ending resolves the stored subscription ID without requiring a customer. Invoice read errors propagate for Meteroid retry (`web/app/api/meteroid/webhook/route.ts` POST; `web/lib/meteroid.ts` `verifyWebhook`).
13. A new invoice/receipt uses the issued buyer snapshot and current/cached default Meteroid seller in the app's shared layout, never Meteroid's PDF. With S3 and a saved key, later downloads/emails reuse those bytes without a Meteroid read. A missing caller key with S3 configured locks and rereads the key before drawing; disabled S3 draws every time. A configured saved-object read failure throws rather than redrawing. Download failures return 502, not PDF-not-ready 409; an unpaid receipt returns 409 before storage access (`documents.ts` `billingDocument`, `renderInvoice`, `renderReceipt`, `finish`; `meteroid.ts` `sellerDetails`; `billing.ts` `documentOf`, `keptPdf`, `invoicePdfFor`, `receiptPdfFor`).
14. Invoice links disable provider notifications/reminders and partial payment, use invoice ID as unique reference, and require a saved phone before creation (`web/lib/billing/razorpay.ts` `ensurePaymentLink`; `web/lib/razorpay.ts` `createInvoicePaymentLink`).
15. Unknown invoice links or money mismatch change nothing and return ignored 200. Accepted-ID retries do not mark again; different payments on an already accepted/paid/void invoice are recorded as duplicates and logged. Remote/local failure gaps are B16 (`web/lib/billing/razorpay.ts` `razorpayInvoicePaid`; `web/app/api/razorpay/webhook/route.ts` POST).
16. Return-URL parameters never mark paid by themselves: studio-only confirmation checks same-org ownership and asks Razorpay; failure gives pending (`web/lib/billing/trpc.ts:41–55`).
17. Daily Razorpay repair covers every **local unpaid** invoice after the Meteroid list succeeds. Failed paid/void link cancellations are not part of that loop (B18) (`billing.ts` `syncOrgInvoices`; `razorpay.ts` `closePaymentLink`).
18. App email/PDF payment guidance never includes bank details. Issued/reminder/paused mail and the unpaid PDF without a URL ask the customer to get a payment link (reply / write to the seller's email). Outside-Razorpay payments are recorded by staff in Meteroid ([Billing](billing.md) rule 20; `email.ts` `BillingEmailArgs`, `billingEmail`; `documents.ts` `renderInvoice`; `billing.ts` `invoicePaid`).
19. Seller reads cache successful results for 10 minutes and throw when entity, legal name or GSTIN is absent, not when the LUT ARN is absent. New export documents print `EXPORT_DECLARATION` and a separate ARN line from entity legal-footer field 11 (placeholder when missing). PDF text/author use the seller, with SAC fixed separately (`meteroid.ts` `defaultInvoicingEntity`, `lutArnOf`, `sellerDetails`; `details.ts` `EXPORT_DECLARATION`; `documents.ts` `billingDocument`, `SAC`, `sheet`, `finish`).

## Edge cases and limits

- External success and local DB failure are not atomic. Meteroid may keep updated details/a top-up despite rollback or lost response; error copy saying “Nothing was changed” refers imperfectly to that boundary (`billing.ts` `locked`, `viaMeteroid`, request functions).
- Pack retries recompute expiry and tax from today's/current details; the same request key can get a different body later. The UI keeps its requestId after an error, but resets it on quantity change, success or remount; it is not a persisted retry ID. Upgrade request keys no longer exist in the app (`billing.ts` `buyPacks`, `packExpiry`; `billing-page.tsx` `BuyPacksDialog.buy`).
- Kind depends on app plan when first seen. A much-delayed first-paid event with several subscription invoices can classify more than one as upgrade; old-subscription invoices first seen after cancellation become other (`billing.ts` `kindOf`, `recordInvoice`).
- Meteroid recent-invoice fetch is one page (50), UI one page (100); there is no pagination. PDFs are kept separately in S3, not as DB bytes (`billing.ts` `keptPdf`). Razorpay repair scans all locally unpaid rows, not unseen Meteroid invoices outside that page. Reminder/overdue/payment steps refresh Meteroid, while call refusal and overview never do (`meteroid.ts` `listInvoices`; `billing.ts` `billingOverview`, `refreshed`, `invoicePdfFor`).
- Banner state has no five-second credit-version invalidation or regular polling; mutations in Billing invalidate its query prefix, but an external payment/pause may need a refetch/reload. Query errors hide the banner (`billing-banner.tsx` `BillingBanner`; `billing-page.tsx` mutations).
- New PDFs preserve the invoice-time buyer snapshot but use current/cached seller details and LUT ARN; stored PDFs reuse the first bytes. A receipt first drawn after a seller edit can therefore differ from the earlier invoice's seller. Without S3 neither document is frozen. Configured first draws are serialized per invoice/document; upload-before-commit failure can leave an unreferenced object, not a successfully returned PDF (`billing.ts` `keptPdf`). Current billing emails still decide recipients. Unsupported scripts are replaced; only descriptions and exemption wording wrap. Long seller/buyer fields, payment URLs, unbroken words/references or many lines/payments can overflow the single page; there is no pagination. Neither PDF adds a second INR-conversion amount; current billing rules do not require one. Payment-history methods use local Razorpay data where present and call all other methods “Bank transfer”; the receipt's headline/closing total is the full invoice total, not a sum/reconciliation of transactions (`billing.ts` `recipients`, `documentOf`; `documents.ts` `safe`, `Sheet.wrap`, `billingDocument`, both renderers).
- Setup dry-run performs reads, suppresses writes. It reads the default invoicing entity and only proposes seeding it when it has no GSTIN. It does not disable Meteroid customer emails or configure Razorpay payment methods/FX conversion. Its PUT price call is outside the shared wrapper's declared method union (`meteroid-billing-setup.ts` price/entity steps; `web/lib/meteroid.ts` `meteroid`). This is a type-contract issue, not a new REST feature.
