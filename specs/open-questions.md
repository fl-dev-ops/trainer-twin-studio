# Open questions and mismatches, all modules

Collected verbatim from each spec's *Mismatches* and *Open questions* sections, for the product owner to decide.
Each answer should land back in the module's spec (and become a test or a fix). Regenerate after editing specs.

## [Authentication and host routing](auth.md)

### Mismatches

- “Invite-only platform” in `web/lib/auth.ts` and the `FounderInvite` schema comment applies to **organization creation**, not account registration: `/sign-up` and Google new-user sign-in are open. `PRODUCT.md` describes the trainer creation workflow but does not specify an auth-method or signup policy. (`web/components/auth/sign-up-form.tsx`, `web/lib/auth.ts`; dependency `dist/api/routes/sign-up.mjs`, `dist/oauth2/link-account.mjs`.)
- Comments describe studio/learner invites as Google sign-in flows, and `docs/guides/users.mdx` describes Google on the org home. This matches the signed-out UI, not a server-enforced Google-only membership rule. An existing matching password session reaches studio Accept invitation; learner acceptance does not inspect provider. (`web/app/auth/invite/page.tsx`, `web/components/auth/invite-form.tsx`, `web/lib/invite/accept.ts`.)
- The auth hook comment says disabled members cannot sign in “any method” and disabling deletes their sessions. Actual behavior is narrower: both restrictions apply only when **all** memberships are disabled. `plans/prod-release-v2.md` §2A similarly summarizes disabling as signing the learner out. (`web/lib/auth.ts` comment versus `web/lib/members.ts` `isDisabledUser`, `setMemberDisabled`.)
- `plans/twin-share-link.md` says the proxy rewrites org hosts to the org route group. Actual proxy behavior is pass-through: root routes already live in that group. The plan's sign-in/sign-up return-URL intent is implemented by the general auth pages/helpers. (`web/proxy.ts`, `web/lib/base-domain.ts`, both sign-in/sign-up pages.)
- `plans/twin-roleplay-db-split.md` §13 calls for learner membership on first sign-in through a link. Auth has no such sign-in hook; org-home invite acceptance or later practice access paths perform membership work. Signing in directly may land on no-org. (`web/lib/auth.ts`, `web/lib/auth-home.ts`, `web/lib/invite/accept.ts`; see [Learner portal](learner-portal.md).)
- Onboarding promises a 3–30-character slug, but `validateOrgSlug`'s optional regex group accepts a single alphanumeric character too. The form blocks fewer than three; API validation/availability can accept one. (`web/lib/slugs.ts`, `web/components/auth/founder-form.tsx`, `web/app/api/onboarding/route.ts`.)
- Onboarding page/API explicitly allow another org for an existing founder, but the invite script rejects existing registered emails and the form unconditionally attempts password sign-up for a new org. The API supports more than the normal script/form path can complete. (`web/app/auth/onboarding/page.tsx`, `web/app/api/onboarding/route.ts`, `web/scripts/founder-invite.ts`, `web/components/auth/founder-form.tsx`.)

### Open questions

- Is “team invites are Google-only” meant as a UI choice or a hard access rule? The invite page says Google, but the accept button only checks email, and `web/lib/auth.ts` has no provider restriction on acceptance. (`web/components/auth/invite-form.tsx`, `web/lib/auth.ts`.)
- Should a password-created user be able to switch immediately to Google? The app trusts Google but does not enable local email verification, while Better Auth 1.7.15 implicit linking requires a verified local email by default. No app linking screen resolves this. (`web/lib/auth.ts`, `web/components/auth/sign-up-form.tsx`; dependency `dist/oauth2/link-account.mjs` `handleOAuthUserInfo`.)
- What is the supported reset-password destination? The server sends reset links, but there is no application page to collect the new password, nor a forgot-password link. Should resetting revoke other login sessions? It currently does not. (`web/lib/auth.ts`, `web/lib/email.ts` `sendPasswordResetEmail`, `web/app/auth/`, `web/components/auth/sign-in-form.tsx`; dependency `dist/utils/password.mjs`.)
- Should founder provisioning support existing users end to end and retry the workspace POST after account creation? The server accepts existing sessions, but the script/form and retry state disagree. Should invite consumption also be conditional inside the transaction? (`web/scripts/founder-invite.ts`, `web/components/auth/founder-form.tsx` `handleStep2Next`, `web/app/api/onboarding/route.ts` POST.)

## [Credits](credits.md)

Resolved Meteroid expiry question: live dev-tenant verification of Meteroid 2.2.1 found stale `wallets/check` credits until usage recount and no `credit_grant.expired` webhook. The app now subtracts full lapsed grants conservatively, schedules sync, and sends zero-minute `expired-<grantId>` events with up to five two-second balance rechecks. If still stale, the stored balance remains conservative at read time; see [Credits — Send and refresh](credits.md#send-and-refresh) (`web/lib/org-credits.ts`).

Resolved funded-wallet race: live verification found `wallet.funded` arrives about two seconds before `wallets/check` counts the new grant. Refresh now waits while a grant's creation is later than balance `as_of`, sharing the bounded five two-second rechecks with expiry recounts. It stores the last read if still behind, so a later sync may be needed; see [Credits — Send and refresh](credits.md#send-and-refresh).

Live studio refresh is now database-only `minutes.version` polling every five seconds: a changed fingerprint invalidates org, Credits page, learner and Users credit queries; the first value does not. No page reload or Meteroid request is needed for the version check. This follows the cache sync, not the webhook itself, and is not a background-tab latency guarantee (`web/lib/minutes-trpc.ts`; `web/components/credits/sidebar-credits.tsx`; [Credits — Live studio refresh](credits.md#live-studio-refresh)).

### Mismatches

- `PRODUCT.md` does not define credit economics, starting amounts or caps. There is no direct product-rule conflict to resolve there.
- `plans/twin-roleplay-db-split.md` §12 describes a separate budget per twin assignment and one role-play attempt with no time limit. Current code uses one org learner balance for both modules and allows repeated role-play practice while credit remains (`web/lib/minutes.ts` `learnerMinutes`; `web/lib/interview-sessions.ts` `activateSession`; `web/lib/pages/learner.ts` `loadSharedSession`; see [Role plays](roleplays.md)).
- `plans/twin-share-link.md` describes granting the link's `minutesPerUser`. `twinAccessByCode` now gives the shared default only to a person without any grant in the org; legacy assignment/link minute fields are not the billing source (`web/lib/twin-access.ts`; `web/lib/minutes.ts`).
- `plans/twin-wiring-and-reliability.md` §2 says assignment minutes allow 1–10,000. Current chosen starting-credit paths enforce 1–360 (`web/lib/twin/trpc.ts` assignments `assign`; `web/app/api/role-play/[slug]/assignments/route.ts`; `giveStartingMinutes`). The generic `DurationInput` still parses up to 10,000, but credit forms/server checks narrow that range (`web/components/duration-input.tsx`; `add-credits-dialog.tsx`; `web/lib/minutes-trpc.ts`).
- `creditsAdded` and history comments call the record “full” or say rows add up to everything added. Actual reads default to 200 rows, and learner history hides take-backs (`web/lib/minutes.ts` `creditsAdded`; `web/components/credits/credits-history-table.tsx`).

### Open questions

- Must “one live call per learner per org” hold under simultaneous starts with different activation keys? `activateSession` closes previous calls and reads balance outside the session-creation transaction; it does not take `locked`'s org lock. Two starts can both pass that sequence. `InterviewSession` has no unique live-call constraint (`web/lib/interview-sessions.ts` `activateSession`; `web/lib/minutes.ts` `locked`; `web/prisma/schema.prisma` `InterviewSession`).
- Should a learner with 1–59 seconds left be able to start? Activation accepts any positive second balance, but shared-session pages floor it to zero and show out-of-minutes; `twinAccessFor` rejects below 60 seconds (`web/lib/interview-sessions.ts` `activateSession`; `web/lib/pages/learner.ts` `loadSharedSession`, `twinAccessFor`).
