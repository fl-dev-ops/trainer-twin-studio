# Role plays

> A role play is a reusable practice scenario: the learner talks to an AI playing a person in a situation. TrainerTwin stores both newer client role plays built from a form and older interview agents. Trainers save, version and assign them; learners use personal links repeatedly while they have credits. Each completed call can have its own report. This spec covers the scenario and its access, not the call machinery (see [Sessions](sessions.md)). Sources: `web/lib/roleplay/skill.ts`, `web/lib/roleplay/trpc.ts`, `web/lib/interview-sessions.ts` `activateSession`.

## Data

The persistent records are defined in `web/prisma/schema.prisma`.

| Record | Important fields and allowed values | Writers |
| --- | --- | --- |
| `Agent` | Globally unique `slug`; `orgId`; `kind = ROLEPLAY`; required `personaId`; `name`, `version` (initially 1), JSON `data`, `order`, `archivedAt`; `visibility` defaults to `public` (route accepts `public` or `private`). | `web/lib/scenario-ingest.ts` `storeSkillAgent`; `web/lib/spec-drafts.ts` `publishSpecDraft`; `web/lib/specs.ts` `saveSpec`, `deleteSpec`; `web/app/api/agents/visibility/route.ts` |
| Builder `Agent.data` | `source`, `skill`, `scenario`, `artifacts` (S3 prefix), `filesHash`; builder input under `scenario.roleplay`, goals/rubric under `after = { report: roleplay, goals, rubric }`. `before` and `tools` hold separate settings. Derived `objective`, `stages`, `config` support common readers. | `web/lib/roleplay/skill.ts` `renderRoleplay`; `web/lib/scenario-ingest.ts` `buildScenario`, `saveRoleplay` |
| `SpecDraft` | Globally unique `slug`, org, `kind`, name, optional `personaSlug`, `agentData`, `groundingData`, `assumptions`, `gaps`; `status = draft / published`, revision initially 1, optional `publishedAt`. | `web/lib/spec-drafts.ts` `saveSpecDraft`, `publishSpecDraft` |
| `SpecDraftRevision` | Previous full bundle keyed uniquely by draft ID and revision. Draft reads return the newest 20 revision summaries. | `web/lib/spec-drafts.ts` `saveSpecDraft`, `readSpecDraft` |
| `SpecVersion` | Previous published JSON data, uniquely keyed by org, entity type (`agents` here), slug and version. Not a separate complete Agent row or persona relationship snapshot. | `web/lib/specs.ts` `saveSpec`, `listVersions`, `readVersion`; `web/lib/scenario-ingest.ts` `storeSkillAgent`; `web/lib/spec-drafts.ts` `publishSpecDraft` |
| `Deployment` | Unique `(orgId, agentId)` and `publicKey`; optional `secretKeyHash`; `status` defaults to `active` (`disabled` also used); `allowedModes` defaults to `chat,voice`; optional origins; rate-limit field defaults to 30/minute. | `web/lib/deployments.ts` `ensureDeployment`; defaults in schema |
| `RolePlayAssignment` | Org/deployment, optional member, recipient email, assigning user, unique random `shareCode`; mode defaults to `voice`; `pending / used / expired / cancelled`; assignment time, required stored expiry, optional `usedAt`. Unique `(deploymentId, memberId)`; email pair has an index, **not** a unique constraint. | `web/lib/invite/roleplay.ts`; `web/app/api/v1/assignments/route.ts`; `web/app/api/v1/assignments/[id]/route.ts`; `web/lib/interview-sessions.ts`; `web/lib/session-activation.ts` |
| `SkillSource` / S3 / Chroma items | Per-version source-document links; versioned skill files in S3; versioned `scenario_item` examples in the org's Chroma collection. | `web/lib/scenario-ingest.ts` `storeSkillAgent`; `web/lib/skill-sources.ts`; `web/lib/main-collection.ts` |

`InterviewSession` owns the individual practice, pinned agent/persona data and report; it references the assignment with a non-unique `assignmentId`. Deleting an assignment sets that reference to null rather than deleting calls. See [Sessions](sessions.md). Source: `web/prisma/schema.prisma` `InterviewSession`, `RolePlayAssignment`; `web/lib/interview-sessions.ts` `activateSession`.

Lifecycles:

- Interview draft: new `draft` → changed saves create revisions → `published`; another changed save returns it to `draft`. Identical saves do not advance revision. Publishing does not delete the draft. (`web/lib/spec-drafts.ts`.)
- Published builder: absent → v1; changed content/persona → previous data snapshot + vN+1; identical content → same version. Archive sets `archivedAt`; skill publication restores it, even when unchanged. (`web/lib/scenario-ingest.ts` `storeSkillAgent`; `web/lib/specs.ts` `deleteSpec`.)
- Assignment: absent → `pending` → `used` on successful runtime initialization. `pending` and `used` both permit repeat practice. Stored `expired` and `cancelled` block access; assigning either again resets it to `pending` with a fresh code. LiveKit failure may return `used` to `pending` only if no other started, non-failed practice exists. Time passing alone no longer changes the status. (`web/lib/invite/roleplay.ts`; `web/lib/interview-sessions.ts` `activateSession`; `web/lib/session-activation.ts`; `web/lib/pages/learner.ts`.)
- Assignment removal is currently deletion: the studio route deletes only pending assignments; the public API deletes any org-owned assignment. Neither DELETE sets `cancelled`. (`web/app/api/role-play/[slug]/assignments/route.ts` DELETE; `web/app/api/v1/assignments/[id]/route.ts` DELETE.)

## How it works

### Build and save a client role play

1. `/roleplay/new` loads the org's persona choices. The form has Scenario, Scoring, Settings and Tools tabs. Scenario includes the situation, hidden truth, learner role, difficulty, reactions, opening, optional brief and example lines. Scoring holds learner goals and rubric. (`web/app/dash/roleplay/new/page.tsx`; `web/components/roleplay/roleplay-builder-page.tsx`; `web/lib/roleplay/trpc.ts` `builder.personas`.)
2. `builder.save` validates the form, Before settings and tool booleans, then calls `saveRoleplay`. New slugs are org-prefixed, made from the name, and get `-2`, `-3`, etc. on collision. Updates keep the supplied slug. The persona must belong to this org. (`web/lib/roleplay/trpc.ts` `builder.save`; `web/lib/scenario-ingest.ts` `saveRoleplay`.)
3. `renderRoleplay` makes the files without an LLM. Steps are opening → objection → close. The opening is always a client item; matching example lines are omitted to avoid repeating that opening. Goals and rubric go only into `after`, not the generated skill or manifest. (`web/lib/roleplay/skill.ts`.)
4. `storeSkillAgent` checks slug ownership and kind before writing. It writes S3, then versioned Chroma examples, then updates PostgreSQL in a transaction. Failure before the database switch leaves the previous live row in place; external writes are not rolled back. After a changed save it keeps current and previous example versions and prunes older ones; pruning failure only warns. (`web/lib/scenario-ingest.ts` `storeSkillAgent`.)
5. A save makes the role play live immediately. There is no builder `SpecDraft` or separate Publish button. Editing Settings/Tools uses `builder.saveSettings`: writes only `data.before` / `data.tools`, without versioning. Switches save immediately; upload-card text has its own Save. Failure shows an error and resets settings to the last saved values. (`web/components/roleplay/roleplay-builder-page.tsx`; `web/lib/roleplay/trpc.ts` `builder.save`, `builder.saveSettings`.)
6. Library cards include every unarchived org ROLEPLAY. Only `source = roleplay-skill` cards open `/roleplay/<slug>`; other sources open `/agents/<slug>`. Builder detail/edit queries accept only that builder source. (`web/lib/roleplay/trpc.ts` `anyRoleplayOf`, `roleplaysOf`, `scenarios.list`, `findRoleplay`.)

### Older interview specs, drafts and publishing

1. `/agents/<slug>/edit` loads the working draft or current published spec; an explicit historical version opens the YAML reader. Invalid or missing requested versions are not found. (`web/lib/pages/spec-resource.ts` `loadSpecResource`.)
2. POST `/api/agents/<slug>/generate` validates name, instructions, opening, persona and interview configuration. It checks voice/knowledge access, calls `generateSpecBundle`, saves a draft and optionally publishes it. Errors in generation/save return a generic 502; validation errors return 400. (`web/app/api/agents/[slug]/generate/route.ts`; `web/lib/spec-generation.ts`.)
3. `saveSpecDraft` parses the bundle, rejects another org's draft, overwrites working data, and saves the old bundle as a revision on a changed update. `publishSpecDraft` refuses unresolved gaps, missing persona and missing/unindexed requested knowledge bases. Persona lookup prefers the org's row, then a global row. Publishing cannot overwrite another org or a different Agent kind. (`web/lib/spec-drafts.ts`; `web/lib/specs.ts` `findOrgOrGlobalPersona`.)
4. Publication copies the agent and grounding into a live Agent, retaining an existing intro video. A change in data or persona snapshots the old data and increments the version; an identical publication keeps it. The draft becomes `published`. Raw `saveSpec` also versions changed YAML but cannot create a new agent without a persona assignment. (`web/lib/spec-drafts.ts` `publishSpecDraft`; `web/lib/specs.ts` `saveSpec`.)

### Assign and deliver a link

1. Studio PUT `/api/role-play/<slug>/assignments` requires an unarchived org ROLEPLAY and 1–100 email entries. It accepts optional starting minutes and a pending-email resend policy. (`web/app/api/role-play/[slug]/assignments/route.ts`.)
2. `inviteToRoleplay` lowercases/deduplicates emails and calls `giveStartingMinutes` before creating assignments. Insufficient org credits refuse that credit grant; existing learner credit grants are not replaced. It ensures a deployment, creates or reopens cancelled/expired assignments, optionally resends pending links, and skips used links. (`web/lib/invite/roleplay.ts`; credit allocation details: [Credits](credits.md).)
3. New/reopened assignments get a random 18-byte base64url code and still store an expiry 30 days ahead. **The expiry date is not enforced** by the page or activation. Emails link to `https://<org>.<base>/s/<code>` and describe repeat practice while minutes last. Email delivery failures are counted but do not undo assignments. (`web/lib/assignments.ts`; `web/lib/invite/roleplay.ts`; `web/lib/email.ts` `sendRolePlayAssignmentEmail`.)
4. Public API POST is idempotent for a pending/used email-scenario pair, returning its existing link without another email. PATCH with no recipient/deployment change is a no-op; a real move checks for a pair clash, resets state and issues a new code, invalidating the old link. Credit and email boundaries are shared, but error responses differ; see [Public API](public-api.md). (`web/app/api/v1/assignments/route.ts`; `web/app/api/v1/assignments/[id]/route.ts`.)

### Open `/s/<code>` and practise again

1. `loadSharedSession` resolves the org from the host. Signed-out people go to sign-in with the link as return path. A role-play code must belong to that org and have status `pending` or `used`. A different recipient gets the switch-account screen. Member-bound assignments match user ID; otherwise email matching is case-insensitive. (`web/lib/pages/learner.ts`; `web/lib/assignments.ts` `assignmentMatchesUser`.)
2. The page blocks a metered learner when fewer than one whole minute is shown. Admin/team are not metered. A valid link loads only its scenario/persona into `SessionView`, including brief assets, context settings, intro video and minutes. Unknown codes can instead resolve to twin access; that is [Twins](twins.md). (`web/lib/pages/learner.ts` `loadSharedSession`; `web/app/(org)/s/[code]/page.tsx`.)
3. POST `/api/sessions` activates the assignment only for its recipient on an active deployment, in an allowed delivery mode. Expiry timestamps and previous completed calls are not rejection conditions. A learner's practice is voice-only. (`web/app/api/sessions/route.ts`; `web/lib/interview-sessions.ts` `activateSession`.)
4. A live `activating` or `active` call on this assignment for this user is resumed with its existing activation key, ID and remaining time. Otherwise a fresh random activation key creates a new practice. A metered learner starting a different call ends their other live calls in the org before checking the new balance. Calls pin agent/persona versions and data; later edits do not rewrite that session. (`web/lib/interview-sessions.ts` `activateSession`; `web/lib/session-context.ts`.)
5. Invited people without membership join the org as role `user` on first activation. Chat initialization failure marks the session failed. LiveKit activation failure closes resources and conditionally resets assignment usage as described above. Neither a failed call nor a completed call consumes the link itself. Call time, closing, charging and recordings belong to [Sessions](sessions.md) and [Credits](credits.md). (`web/lib/interview-sessions.ts`; `web/lib/session-activation.ts`.)

### Context before and during a call

- Role plays with `data.before` use its screen-share, pre-upload and during-upload switches. Pre-upload is optional, at most one file in resolved settings; all switches default off. `beforeSettings` reads `twinSettings` as a fallback, but non-twins enter this settings path only when a `before` object exists. (`web/lib/context-upload.ts` `usesBeforeSettings`, `beforeSettings`, `contextUploadFromAgentData`.)
- Older role plays without `before` use `config.context`, including the first stage requiring context. A required document makes the upload card appear and prevents the browser starting without it. `max_files` resolves to 1–5. These older defaults accept documents, require whole-screen sharing and disable mid-call attachments. (`web/lib/context-upload.ts` `contextConfigFromAgentData`, `resolveContextUpload`; `web/components/session-view.tsx`.)
- Session start checks ready documents in the org, ownership when present, and PDF/image type and size. Supplying a document to a Before-configured role play with pre-upload off is rejected. The browser accepts only an entire screen, not a tab/window, when sharing is enabled; document-required and sharing behaviour have server-boundary limits noted below. (`web/lib/interview-sessions.ts` `sessionSnapshot`, `activateSession`; `web/components/session-view.tsx` `screenShareSurface`, screen-share effects.)
- Before uploads accept PDF/PNG/JPEG/WebP up to 10 MB. During uploads accept PDF up to 10 MB or images up to 5 MB. The attach route reads the session's snapshotted policy. File storage and expiry belong to [Platform](platform.md), not scenario knowledge. (`web/lib/context-upload.ts` `uploadProblem`, `uploadAllowed`; `web/app/api/sessions/[id]/documents/route.ts`.)

### Reports, lists and scoring

1. Completion dispatches by `after.report`: builder role plays use the role-play workflow; older role plays with no After block use the legacy session-report job. Abandoned role plays are not scored by `processEndedSession`. (`web/lib/session-processing.ts`; `web/lib/session-after.ts`.)
2. The workflow claims `reportStatus` from null/none/failed to generating, deduplicating concurrent completion notifications. It waits up to twelve 10-second intervals for the final agent transcript, then uses the saved transcript. Generation has three retries; success stores a `kind = roleplay` report and marks completed, failure marks failed. (`web/lib/schedule-report.ts`; `web/workflows/roleplay-session-report.ts`; `web/workflows/roleplay-session-report-steps.ts`; `web/lib/roleplay/session-report.ts`.)
3. Scoring uses the start-time snapshot's brief, goals and rubric, falling back to live agent data for older snapshots. Only learner speech is scored. The report includes summary/tags, key moments, next-time focus, goal results (`met / partly / not_met`) and rubric points. Missing goals default to not met, missing rubric rows to zero; points are rounded and clamped. Overall score is rounded earned/available × 100, not the model's proposed score when a rubric exists. No transcript fails; a transcript with no learner speech produces zero points. Goal/score consistency is a model instruction, not a deterministic cross-check. (`web/lib/roleplay/session-report.ts` `loadRoleplayReportInput`, `buildRoleplayReport`, `toRoleplayReport`.)
4. The report page labels score ≥70 as Pass, otherwise Not yet. “Biggest opportunity” is `focusNextTime`. “What went well” uses up to two best rubric rows at ≥60%; “To work on” uses up to two weakest at <80%. These are UI derivations, not additional stored verdicts. The page includes a transcript and quietly polls pending reports. (`web/components/roleplay/roleplay-session-report-page.tsx`.)
5. Role-play session lists include old interview scenarios, whose reports open `/sessions/<id>` instead. New builder reports open `/roleplay/sessions/<id>`. Lists require a started, non-deleted session and take the newest 200. Builder detail statistics use at most 200 sessions and show 20 recent ones. They are not lifetime totals beyond that limit. (`web/lib/roleplay/trpc.ts` `sessions.list`, `scenarios.get`.)
6. Roleplay users are the union of invitations and started, non-deleted sessions for all org role plays. Rows merge by lowercase email, count distinct role plays and sessions, and show shared credits (null for admin/team). Invitations include all statuses and archived agents; this is not a list of only currently assigned learners. Rows sort by session count descending, then name. (`web/lib/roleplay/trpc.ts` `users.list`, `invitesFor`; `web/components/roleplay/roleplay-users-page.tsx`.)

## Rules

1. Studio role-play procedures reject signed-out callers, org-less callers and learners; all queries use the current org. `hideRoleplay` is not checked by `studioProcedure`. (`web/lib/trpc.ts`; `web/lib/roleplay/trpc.ts`.)
2. Builder detail/edit requires `kind = ROLEPLAY`, `source = roleplay-skill`, same org and no archive timestamp. Older interview agents remain readable through `/agents`; twins must not be overwritten by role-play publication. (`web/lib/roleplay/trpc.ts` `findRoleplay`; `web/lib/scenario-ingest.ts` `storeSkillAgent`; `web/lib/spec-drafts.ts` `publishSpecDraft`.)
3. Builder input requires a name (≤120 characters), org persona, situation (≤4000), learner role (form schema ≤200; stored manifest ≤100), opening (≤1000), and one of easy/medium/hard/hardest. There must be 1–5 goals and 1–8 rubric criteria; each point maximum is an integer 1–100. There is **no requirement that rubric maxima sum to 100**. Each reaction list has at most 12 entries; optional examples at most 20. (`web/lib/roleplay/skill.ts` `roleplayBuilderSchema`; `web/lib/scenario-ingest.ts` `saveRoleplay`.)
4. Rendering is deterministic; client and learner item roles differ from twin trainer/learner items. Scoring goals/rubric must not be inserted into generated During instructions. (`web/lib/roleplay/skill.ts` `renderRoleplay`, `roleplayItemSchema`; `chat/agent/lib/roleplay.ts` `roleplaySkill`, `formatRoleplaySession`.)
5. A changed full builder save increments the version once and snapshots old data. Equal content/persona keeps the version. Settings-only saves do not increment it. (`web/lib/scenario-ingest.ts` `storeSkillAgent`; `web/lib/roleplay/trpc.ts` `builder.saveSettings`.)
6. Publishing a draft with gaps or unindexed/missing requested knowledge is refused. Publishing over another org or a twin is refused. An org persona is preferred over a matching global persona. (`web/lib/spec-drafts.ts` `publishSpecDraft`; `web/lib/specs.ts` `findOrgOrGlobalPersona`.)
7. `public / private` controls inclusion in GET `/api/portal/agents`; it is not an assignment access check. That catalog lists runnable ROLEPLAY agents. Private role plays can still be assigned and started through valid links. (`web/app/api/agents/visibility/route.ts`; `web/app/api/portal/agents/route.ts`; `web/lib/external-api-assignments.ts` `findScenario`; `web/lib/interview-sessions.ts` `activateSession`.)
8. `ensureDeployment` returns the existing org-agent deployment without resetting disabled status or settings. Concurrent creation retries a unique-conflict lookup. Assignment activation refuses disabled deployments and disallowed requested modes. (`web/lib/deployments.ts`; `web/lib/interview-sessions.ts` `activateSession`.)
9. Assignment access accepts only pending/used, checks org and recipient, and does not enforce `expiresAt`. Completed or abandoned calls do not block another practice. A live call on the same link is resumed, not deliberately replaced. Credits still limit time. (`web/lib/pages/learner.ts` `loadSharedSession`; `web/lib/interview-sessions.ts` `activateSession`.)
10. Studio invitation batches accept 1–100 email entries, normalize and deduplicate them, and resend a pending email only when requested. Existing used assignments are skipped, not reopened. (`web/app/api/role-play/[slug]/assignments/route.ts`; `web/lib/invite/roleplay.ts`.)
11. Public assignment POST returns the same pending/used pair without email; a cancelled/expired pair gets a new code. A real PATCH cannot move onto an existing email-deployment pair (409). Email failure does not roll back the assignment. (`web/app/api/v1/assignments/route.ts`; `web/app/api/v1/assignments/[id]/route.ts`; `web/lib/external-api-assignments.ts` `emailAssignment`.)
12. API assignment practice counts include all started, non-failed sessions for that assignment, including active/abandoned calls. `lastPracticedAt` is their maximum start time, not completion time. Sessions can be filtered by assignment ID. (`web/lib/external-api-assignments.ts` `assignmentDetails`; `web/app/api/v1/sessions/route.ts`.)
13. An archived agent cannot start a new call; previous versions and past sessions remain. Archive does not delete the assignment. (`web/lib/specs.ts` `deleteSpec`; `web/lib/interview-sessions.ts` `sessionSnapshot`; `web/prisma/schema.prisma`.)
14. `hideRoleplay` is true only for JSON boolean true in org metadata. It hides the sidebar group, redirects `/roleplay/*` and persona pages to `/twin`, and removes assigned role plays from org home. It does not revoke existing links or API access. (`web/lib/org.ts` `parseHideRoleplay`, `requireRoleplayOrg`; `web/components/app-sidebar.tsx`; `web/app/dash/roleplay/layout.tsx`; `web/app/dash/personas/layout.tsx`; `web/lib/pages/org-home.ts`; `web/lib/pages/learner.ts`; `web/lib/roleplay/trpc.ts`.)
15. Tools default off, including missing individual keys. Canvas, code editor, PDF preview and choice are separate switches. Runtime loading and backstop guards use the snapshotted settings, so a live call does not gain tools after a save. (`web/lib/agent-tools.ts`; `web/lib/session-context.ts`; `chat/agent/tools/workspace.ts`; `chat/agent/lib/workspace-tools.ts`; see [Voice agent and chat](voice-agent-and-chat.md).)

## Talks to

- **Personas:** a builder references an existing org persona, not a copied persona. Interview publication can fall back to global personas. A call pins persona data/version at activation. (`web/lib/scenario-ingest.ts` `saveRoleplay`; `web/lib/spec-drafts.ts` `publishSpecDraft`; `web/lib/interview-sessions.ts`; see [Personas and voice](personas-and-voice.md).)
- **PostgreSQL, S3 and Chroma:** PostgreSQL holds live data/history/access; versioned S3 stores the files; Chroma serves versioned example lines. Ingest also records knowledge source links. (`web/lib/scenario-ingest.ts` `storeSkillAgent`; see [Knowledge](knowledge.md), [Platform](platform.md).)
- **Chat and LiveKit:** activation hands over session ID/org/mode and pinned data. Client mode plays the scenario, uses difficulty/guard rules and can `end_call`; older no-skill agents keep interview mode. (`web/lib/interview-sessions.ts`; `web/lib/session-activation.ts`; `chat/agent/lib/roleplay.ts`; see [Sessions](sessions.md), [Voice agent and chat](voice-agent-and-chat.md).)
- **Workflow / report model:** completed builder calls supply transcript, saved brief, goals and rubric; return a stored report. Interview generation uses `generateSpecBundle`; builder rendering does not use a model. (`web/workflows/roleplay-session-report.ts`; `web/lib/roleplay/session-report.ts`; `web/lib/report-model.ts`; `web/lib/spec-generation.ts`.)
- **Credits and email:** invitation grants starting credits through the credit ledger, then sends the personal link through `sendRolePlayAssignmentEmail`; practice debits belong to session finalization. See [Credits](credits.md), [Invites and emails](invites-and-emails.md). (`web/lib/invite/roleplay.ts`; `web/lib/interview-sessions.ts`.)

## Edge cases and limits

- Assignment-email uniqueness is enforced by lookups, not a DB unique email-pair constraint. The public POST contains a `ponytail` comment assuming serialized dashboard/API requests. Concurrent requests can race. The same-link live-call lookup also precedes session creation, without an assignment-wide transaction or unique live-assignment key. The normal resume path is not proof of race-free single-call creation. (`web/prisma/schema.prisma`; `web/app/api/v1/assignments/route.ts`; `web/lib/interview-sessions.ts` `activateSession`.)
- The builder schema allows a 200-character learner role, but `saveRoleplay` parses its rendered manifest with a 100-character role limit; persona-derived client roles also hit that manifest limit. Such input can pass the form schema but fail saving. (`web/lib/roleplay/skill.ts` `roleplayBuilderSchema`; `web/lib/scenario-ingest.ts` `scenarioManifestSchema`, `saveRoleplay`.)
- A required legacy document is enforced in `SessionView`, not by a missing-document check in `activateSession`. Sharing is a browser media rule, not a server proof that a screen is being shared. The session POST forwards only `contextId`, although SessionView sends `contextIds` and the underlying activation helper supports multiple IDs. (`web/components/session-view.tsx`; `web/lib/interview-sessions.ts` `sessionSnapshot`, `activateSession`; `web/app/api/sessions/route.ts`; `web/lib/session-activation.ts`.)
- The link page uses whole minutes and blocks below 60 seconds; activation itself only rejects a balance ≤0 seconds. Resuming happens before that new-call balance check. (`web/lib/pages/learner.ts` `loadSharedSession`; `web/lib/interview-sessions.ts` `activateSession`.)
- Link-page loading does not check deployment status or agent archive; activation checks deployment status and `sessionSnapshot` excludes archived agents. A link can therefore render its prejoin page but fail to start. The old public catalog also lacks an archive filter in both its runnable lookup and final query. (`web/lib/pages/learner.ts`; `web/lib/interview-sessions.ts`; `web/lib/specs.ts` `listRunnableSpecs`; `web/app/api/portal/agents/route.ts`.)
- Settings-only writes mutate live Agent data without making a `SpecVersion`; a later script save snapshots those latest settings. Session snapshots still protect calls already started. Old Chroma examples beyond the previous version are pruned, so very old in-flight calls may retain instructions but lose retrievable example items. (`web/lib/roleplay/trpc.ts` `builder.saveSettings`; `web/lib/scenario-ingest.ts` `storeSkillAgent`; `web/lib/session-context.ts`.)
- Org-home role plays are assigned pending/used links, not the public catalog; they do not filter visibility or the stored expiry date. Studio users do not get this learner list. (`web/lib/pages/org-home.ts` `loadOrgHome`.)
- The report-model helper has an explicit `shortcut:`: Workflow reports use the AI gateway path, unlike the older report's direct-Gemini option. A missing gateway-compatible key is fatal. (`web/lib/report-model.ts` `callReportModel`.)

## Open questions

- Should ingestion-created ROLEPLAY skills be first-class runnable role plays? `ingestScenario` writes `source = scenario-ingest` and requires an own persona; the runtime recognizes any ROLEPLAY with `data.skill`. But `isRunnableAgentData` recognizes skill-only role plays only for `roleplay-skill`, and the library routes every other source to the old interview editor. No `after.report = roleplay` is added by this ingest path. Pointers: `web/lib/scenario-ingest.ts` `ingestScenario`, `buildScenario`; `web/lib/specs.ts` `isRunnableAgentData`; `web/lib/roleplay/trpc.ts` `scenarios.list`; `chat/agent/lib/roleplay.ts` `roleplaySkill`; `web/lib/session-after.ts`.
- Is `hideRoleplay` meant only to hide discovery, or to revoke access? Page/sidebar/home guards enforce hiding, but the tRPC router, invitation APIs, public catalog and existing `/s/` links do not consult the flag. Pointers: `web/lib/org.ts` `requireRoleplayOrg`; `web/lib/pages/org-home.ts`; `web/lib/roleplay/trpc.ts`; `web/app/api/portal/agents/route.ts`; `web/lib/pages/learner.ts`.
- Should Roleplay users and detail member lists exclude cancelled/expired invitations and archived agents? The new `invitesFor` queries include them, whereas older `listSpecSummaries` counts only pending/used assignments. Pointers: `web/lib/roleplay/trpc.ts` `users.list`, `scenarios.get`, `invitesFor`; `web/lib/specs.ts` `listSpecSummaries`.
- Is legacy `memberId` binding still intended to be populated at first use? `assignmentDetails` comments say it is bound when used; current activation creates org membership and updates assignment status/time but does not write `memberId`. Recipient email remains authoritative for unbound links. Pointers: `web/lib/external-api-assignments.ts` `assignmentDetails`; `web/lib/interview-sessions.ts` `activateSession`, `ensureLearnerMember`; `web/lib/assignments.ts` `assignmentMatchesUser`.
